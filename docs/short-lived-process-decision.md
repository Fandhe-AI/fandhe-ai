# 短命プロセス対応方針の決定（#172・TASK-13.2）

イシュー #172「docs(backend): TASK-13.2 短命プロセス対応方針の決定」に対応する。
TASK-13.2（`docs/spec/05-tasks.md:379-384`）の内容「TASK-13.1 の実測結果を踏まえ、短命プロセスのユースケース
（CLI・サーバーレス関数等）を初期スコープに含めるかどうかを決定する。未対応と決定した場合は
`04-requirements.md` の除外事項への追記を次フェーズへの申し送り事項として記録する（本タスクでは
`04-requirements.md` 自体は編集しない）」を満たすための決定記録である。判断材料は前提タスク
TASK-13.1（#169〜#171）の実測記録 `docs/perf/startup-cost-measurement.md` であり、同記録「後続」節
（`docs/perf/startup-cost-measurement.md:213-217`）が「TASK-13.2（#172）が本記録を入力とする」と明記している。

## 決定

**短命プロセスユースケース（CLI・サーバーレス関数等）は、初期スコープに含めない（未対応）。**

REQ-13 の受け入れ基準 4 点目（`docs/spec/04-requirements.md:264`「短命プロセスのユースケース
〈CLI・サーバーレス関数等〉を初期スコープに含めるかどうかを、本要件の対応方針決定と合わせて明示すること
〈未対応の場合は除外事項に追記すること〉」）に対応し、本ドキュメントの「除外事項への追記文案（申し送り）」
節に追記文案を記録する。

## 決定の位置づけ（承認経路）

本イシューは `human-required`（担当: 人間）に分類されている。本エージェントは自動運転モードで動作しており
ユーザーへの質問・承認待ちができないため、決定内容は下記「判断材料」に基づき安全側（実測が伴わない対象を
「対応済み」と宣言しない側）に倒して起案し、**本決定を含む PR のレビュー・マージ（人間）をもって決定の
正式承認とみなす**。マージ前の本ドキュメントはあくまで起案であり、レビューで判断が覆った場合は本ドキュメント
を差し替える。

## 判断材料

TASK-13.1 実測記録（`docs/perf/startup-cost-measurement.md`）の要点:

| バックエンド | 状態 | 要点（出典） |
|------------|------|------|
| CPU | 実測済み | コールド／ウォームがほぼ同値（run1 first_kernel 中央値: コールド 2.117ms／ウォーム 2.132ms、差 0.015ms。`docs/perf/startup-cost-measurement.md:54-57,85-91`）。JIT を持たないため、短命プロセスでも起動コストが実用上の障害にならないことをミリ秒オーダーで確認済み |
| CUDA | 実機未実施 | NVRTC 実行時コンパイルがディスク非永続の契約として残存する（`backend-cuda/src/nvrtc.rs`）。動的ロード契約自体は実地確認済みだが（`docs/perf/startup-cost-measurement.md:93-108`）、実際のカーネル起動コストの定量値は DGX Spark GB10 実機実測が必要で、本セッションでは未実施 |
| Metal | 実機未実施 | ドライバ側 JIT キャッシュに相当する永続機構を `crates/backend-metal` 側で明示的に扱っておらず、CPU 同様コールド／ウォーム差がほぼ生じない可能性があるが、これも実機実測で確認する必要があり未実施（`docs/perf/startup-cost-measurement.md:132-143`） |

実測記録自身が「CUDA/Metal 実機転記が完了するまでは、本記録の CPU 実測部分・構造差分の定性分析のみを
判断材料として扱う」（`docs/perf/startup-cost-measurement.md:216-217`）と明記しており、本決定もこの制約を
そのまま引き継ぐ。REQ-13 が主眼とする「頻繁なプロセス起動を伴うユースケース」（`docs/spec/04-requirements.md:257`）
は GPU バックエンド（CUDA・Metal）を含む構成が実運用上の主対象であり、その定量実測が欠けたまま
「初期スコープに含める」と宣言することは安全側の判断ではない。

参考として、v1（Burn/CubeCL・DGX Spark GB10 実機）の起動コストはウォーム時 PyTorch 比約 1.9〜2.7 倍・
コールド時約 21〜24 倍（`docs/spec/04-requirements.md:258`、PoC-5）だが、これは CubeCL の autotune 探索・
プロセスごとのシェーダー JIT コンパイルに起因する v1 固有の構造であり、v2（完全自作コア）はいずれも構造的に
持たない設計（`docs/dispatch-rules-design.md` の静的ディスパッチ規則、`docs/perf/startup-cost-measurement.md:171-177`
「構造差分」節）である。このため v1 実測値をそのまま v2 の短命プロセス対応可否の根拠にはできない
（構成が異なるハードウェア・ワークロードでの計測であり単純比較不可。同記録「計測前提の非対称性」節
`docs/perf/startup-cost-measurement.md:186-199` 参照）。

## 根拠のまとめ

1. **判断材料が CPU 実測のみ**: CUDA/Metal の実機実測が未転記であり、REQ-13 が主眼とする GPU バックエンドの
   起動コストを定量確定できていない。定量根拠を欠いたまま「対応（初期スコープに含める）」を宣言することは
   安全側の判断ではない
2. **CPU 経路の実用性は事実として付記する**: CPU バックエンドはコールド≒ウォーム・ms オーダーで、短命プロセス
   でも構造的な問題がないことを実測済みの事実として記録する。ただし本決定はこれをもって「初期スコープでの
   正式サポート」を宣言するものではない（GPU バックエンドを含む構成全体の判断が必要なため）
3. **再判定トリガーを明示する**: 下記「再判定トリガー」節の条件が満たされた時点で本決定を再検討する
4. **申し送りメモを残す**: `docs/spec/04-requirements.md`（正本 submodule）は本タスクでは編集しない
   （TASK-13.2 の制約・`out-of-scope-tracking.md` 準拠）。除外事項への追記は spec リポジトリ
   （Fandhe-AI/rust-ai-library-spec）側での対応とし、追記文案を下記に記録する

短命プロセスユースケースを初期スコープに含めるかどうかを判断し直す。
