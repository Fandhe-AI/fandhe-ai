# 決定記録の雛形（保守・運用チェックリスト）

Phase 2 以降の設計・決定記録が使う雛形である。各記録は本書の「保守・運用チェックリスト」9 節を必ず持つ（横断ルート #3711・Phase 1 #3712 の方針。本書の新設はイシュー #3716）。

- 正本は各決定記録であり、本書は書式だけを定める
- 本書自体は承認の根拠にならない。承認の根拠は所有者コメントの URL と日付を各記録に書く。実際に得ていない承認は書かない
- 節番号 1〜9 は固定する。後続の設計 issue はこの番号で引用する

## 使い方

- **新規の決定記録**: 「保守・運用チェックリスト」の 9 節をそのまま新節としてコピーし、`docs/<領域>-<名前>-decision.md` へ置く。冒頭に「位置づけ・承認根拠」「境界」「推奨」を書く（先例: `docs/facade-speculative-decoding-batching-design.md` §1）
- **既存の決定記録への追記**: 新節 `## N. 保守・運用チェックリスト（イシュー #X）` を足し、その下に `### N.1`〜`### N.9` として 9 節を入れる。既存節の本文は書き換えず追記だけにする（`docs/compat-api-scope.md` §5 の「本文は書き換えない」と同じ扱い）
- **該当しない節**は削除せず「該当なし」と理由を 1 行書く（監査で抜けと区別するため）
- **実機で測れなかった値**は「未実測」と書く。Linux や M4 Max 開発機の代替値で pass にしない。cfg により 0 本しか実行されなかった結果も pass の根拠にしない
- 実機ホスト名は書かず `<cuda-node>`・`<metal-node>`・`<rocm-node>` で表す。認証情報・インスタンス識別子・個人のパスも書かない

## 推奨と「所有者へ戻す論点」の書式

- 推奨は「実装する」か「対象外にする」のどちらかを、理由つきで 1 つ書く。「設計で判断」とされた項目（`FitConfig` 形・低精度演算の配置等）は必ずこの 2 択を書く
- 選択肢は次の表にし、推奨案に印を付ける

| 案 | 内容 | 利点 | 欠点・影響 |
|----|------|------|-----------|
| A（推奨） | | | |
| B | | | |

- 所有者へ戻す論点は次の表で書く

| 点 | 選択肢 | 推奨 | 確認がないときの扱い |
|----|--------|------|----------------------|
| | | | 確認があるまで実装へ進めない（保留のまま保護ガードを維持） |

- 「確認がないときの扱い」の既定は上記（fail-closed）とする
- 論点が無いときは「所有者へ戻す点 | なし（理由）」と 1 行書く（先例: 同 doc §19.10）
- 実装中に決められない点が見つかったら「なし」とせず表へ足して所有者へ戻す
- 承認の記録は `承認: <URL>・<日付>` の形で書く

## 記録に必ず付ける周辺項目

- セキュリティ観点: OWASP Top 10 のうち該当する項目と対策（外部入力の検証順・秘密情報を書かない等）
- スコープ外: 現記録で扱わない事項と追跡先 issue（`.claude/rules/out-of-scope-tracking.md`。無断で起票せず所有者の承認を得る）
- `Closes`／`Refs` の使い分け: 実測で完了条件を満たした PR だけ `Closes`、それ以外は `Refs`
