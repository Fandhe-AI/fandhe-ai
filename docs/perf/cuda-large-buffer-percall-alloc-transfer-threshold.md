# 大容量バッファ per-call アロケーション＋転送の閾値サイズ・二峰性（#1146）

イシュー #1146（親 #1130・#1102 配下）の受け入れ条件に対応する。
`docs/perf/cuda-wmma-f16-perf-triage.md` §3.3〜§4.2（#1123・GB10 実測
2026-09-03）で観測した、per-call 経路（`clone_htod`×2 → `alloc_zeros::<f16>`
→ `synchronize` → `clone_dtoh`）の「転送のみ」計測が dim2048（A/B/C 各
8 MiB・f16）で 0.45 ms なのに対し dim4096（各 32 MiB）では約 261〜263 ms
（3 回連続で安定）へ跳ね、`CudaMmaGemm::run_f16` 合算計測が 1 回目
0.0185 s・2 回目 0.260 s の二峰性を示した外れ値の、閾値サイズ・発生条件の
特定を担う。

## 1. 背景

`docs/perf/cuda-wmma-f16-perf-triage.md` §3.3〜§4.2 の観測（要約）:

| 指標 | dim=2048（各 8 MiB） | dim=4096（各 32 MiB） |
|---|---|---|
| 転送のみ計測（3 回連続） | 0.45 ms 前後 | 約 261〜263 ms（安定） |
| `CudaMmaGemm::run_f16` 合算 | — | 1 回目 0.0185 s／2 回目 0.260 s（二峰性） |

関連する既存事実（`docs/perf/cuda-fresh-gemm-n2048-overhead-diagnosis.md`
§6.2・§6.4。f32・N=4096・64 MiB 出力での phase breakdown）:

- 未タッチ `Vec` への D2H: 539 ms
- 事前タッチ済み `Vec` への D2H: 1.15 ms（事前タッチ自体は 46 ms）

この非対称が f16 dim4096（32 MiB×3）の外れ値にも寄与しているかを、本
イシューのフェーズ分解で確認した（§5 で確証）。

### 2.2 フェーズ分解

| # | フェーズ | 内容 | 対応仮説 |
|---|---|---|---|
| P0 | 参照（転送のみ合算） | `clone_htod`×2・`alloc_zeros`・`synchronize`・`clone_dtoh` | #1123 実測との接続 |
| P1 | デバイス確保＋解放のみ | `unsafe { stream.alloc::<f16>(n) }` → drop | H-B（`cuMemAllocAsync` プール） |
| P2 | `alloc_zeros` のみ | memset 込み | H-B |
| P3 | H2D のみ | `clone_htod` | H-C（ページャブル転送） |
| P4 | D2H（宛先: 毎回新規 `Vec`） | `clone_dtoh` | H-A（未タッチページ） |
| P5 | D2H（宛先: 事前タッチ済み再利用 `Vec`） | `memcpy_dtoh` | H-A の対照 |
| P6 | ホスト `Vec` 確保＋タッチ＋解放のみ | GPU 非関与 | H-A の純ホスト成分 |

連続 3 ラン（各ラン warmup 20・計測 20）を実行し、ラン直前に cold
（warmup なし）1 回目を `Instant` で別途記録した。二峰性の可視化として
`min`／`q1`／`median`／`q3`／`max`・`slow_count`（サンプルが `min` の
10 倍を超えた回数）を記録した。総実行時間短縮のため、フル P0〜P6 は
昇順パスのみで確保し、降順パスは P0（参照）・P4／P5（H-A 判定に必要な
最小集合）・P6 に絞った。

`16 MiB×3`（合計 48 MiB）vs `24 MiB×2`（合計 48 MiB）vs `48 MiB×1` の
H2D 合算（`clone_htod` を本数分連続実行）を比較し、「単体バッファサイズ」
と「合計転送サイズ」のどちらが閾値を支配するかを切り分けた。

## 4. 事実（実測データ）

### 4.1 P6（ホスト `Vec` タッチのみ・GPU 非関与）: サイズ別 median（昇順パス）

glibc の mmap しきい値効果が**純ホストコードのみ**で再現するかを見る
対照実験。GPU・CUDA は一切呼ばない。

| size_mib | median_ms（asc） | median_ms（desc） |
|---:|---:|---:|
| 8 | 0.077 | 0.075 |
| 16 | 0.166 | 0.174 |
| 24 | 0.289 | 10.385（※§4.4 参照） |
| 28 | 0.357 | 0.398 |
| 30 | 0.401 | 0.421 |
| 31 | 0.412 | 0.412 |
| **32** | **12.999** | **13.577** |
| 33 | 14.485 | 13.878 |
| 36 | 15.590 | 15.629 |
| 40 | 17.635 | 13.216 |
| 48 | 20.298 | 19.949 |
| 64 | 20.588 | 27.345 |

**31 MiB → 32 MiB で median が約 30〜40 倍に跳ぶ**（asc: 0.412 ms →
12.999 ms、desc: 0.412 ms → 13.577 ms）。この閾値は**両走査順で完全に
一致**し、かつ P6 は GPU・CUDA API を一切呼ばないため、原因は
**純粋にホスト側**（glibc アロケータの mmap しきい値。64-bit Linux の
`M_MMAP_THRESHOLD` 動的既定上限 32 MiB）にあると確定できる。

| 8 | 0.149 | 0.148 | 1.0x |
| 16 | 0.290 | 0.290 | 1.0x |
| 24 | 0.432 | 0.432 | 1.0x |
| 28 | 0.503 | 0.503 | 1.0x |
| 30 | 0.539 | 0.538 | 1.0x |
| 31 | 0.556 | 0.556 | 1.0x |
| **32** | **17.96** | 0.575 | **31x** |
| 33 | 19.27 | 0.593 | 32x |
| 36 | 20.91 | 0.646 | 32x |

| 48 | 23.88 | 0.859 | 28x |
| 64 | 30.68 | 1.143 | 27x |

P5（宛先を計測外で 1 回だけ確保・全ページタッチしてから使い回す）は

### 4.4 二峰性（順序依存の追加スパイク。24 MiB・降順パス）

§4.1 の 24 MiB desc 行に現れる異常値の内訳（同一プロセス内の連続 3 ラン）:

| size_mib | order | run_idx | cold_ms | median_ms（p0） | max_ms（p0） | median_ms（p4） |
|---:|---|---:|---:|---:|---:|---:|
| 24 | desc | 0 | 16.41 | 11.75 | 12.10 | 11.14 |
| 24 | desc | 1 | 15.73 | **240.18** | **253.53** | **240.35** |
| 24 | desc | 2 | 15.79 | 10.54 | 11.86 | 11.17 |

24 MiB は §4.1／§4.2 の閾値（32 MiB）を下回るサイズだが、**降順パス**
（64→48→…→32→31→…→24 の順で実行し、32 MiB 以上のフェーズを直前に
実行した状態）でのみ、3 ラン中 1 ラン（run_idx=1）だけ p0／p4 の
**median が約 240 ms・max が約 254 ms** まで跳ね上がった（それ以外の
2 ラン・および昇順パスの同サイズでは 10〜12 ms 程度の「32 MiB 通過後の
やや高止まりしたベースライン」に留まる。`slow_count`〈サンプルが `min`
の 10 倍を超えた回数〉列はいずれの行も 0 のままで、40 サンプルの**大半
または全体**が一様に遅くなるモード切り替えであり、少数の外れサンプルの
混入ではない）。これが元の #1123 で観測された「二峰性」に対応する現象
であり、**32 MiB 以上のフェーズを経由した直後の降順走査でのみ・確率的に
発生する**（3 回に 1 回。asc では未発生）。§4.6 の `MALLOC_MMAP_
THRESHOLD_` 固定実験では、しきい値を動かすとこの種のスパイクが発生する
サイズ・頻度が変化することを確認しており（§4.6）、glibc ヒープの内部
状態（アリーナのフラグメンテーション・`mmap`/`munmap` に伴うカーネル側
処理）に起因する確率的な追加コストであると推定される（未確定。詳細は
§5 H-A 節）。

### 4.5 固定合計サイズ比較（`large_buffer_percall_fixed_total_size_comparison`）

| label | buffer_count | per_buffer_mib | total_mib | median_ms |
|---|---:|---:|---:|---:|
| 16x3_total48 | 3 | 16 | 48 | 0.879 |
| 24x2_total48 | 2 | 24 | 48 | 0.869 |
| 48x1_total48 | 1 | 48 | 48 | 0.861 |

合計転送量が同じ 48 MiB でも、**単体バッファサイズが 32 MiB 未満なら
（16 MiB×3・24 MiB×2 いずれも）閾値効果は発生しない**。したがって
閾値は「単体バッファサイズ」に対して働き、「合計転送サイズ」には
働かない（受け入れ条件 3 の一部に対応する結論）。

### 4.6 `MALLOC_MMAP_THRESHOLD_` 固定時の挙動変化（確証実験）

`env MALLOC_MMAP_THRESHOLD_=67108864`（64 MiB 固定。glibc のヒープ
成長ヒューリスティックによる動的しきい値調整を止め、mmap への切替を
64 MiB に固定）で同一バイナリを再実行したところ、**32 MiB 単体では
もはや閾値効果が起きず**（brk ヒープ経由になったため）、代わりに
**より小さいサイズ（28〜32 MiB 帯）で数百 ms 規模のスパイクが不規則に
出現するようになった**（例: `p0_transfer_only,28,asc,0` の median が
285.53 ms、`p4_d2h_fresh_vec,32,asc,1` の median が 324.44 ms。既定
しきい値〈32 MiB〉での同サイズはいずれも 1 ms 未満〜20 ms 程度)。この
挙動変化（しきい値を動かすと、閾値の位置だけでなく確率的スパイクの
発生パターンそのものが変わる）は、**問題の根がホスト側のメモリ
アロケータ（glibc）にある**という H-A の結論を強く支持する一方、
mmap しきい値だけで全ての変動を説明しきれないこと（brk ヒープの成長・
断片化に起因する追加コストが別途存在すること）を示している。

## 5. 仮説

- **H-A（ホスト側・未タッチページ／glibc mmap しきい値）: 支持
  （§4.1・§4.6 のみで確定。§4.2 は再実測待ち）**。§4.1（P6・GPU 非関与
  でも 32 MiB で閾値）・§4.6（`MALLOC_MMAP_THRESHOLD_` を動かすと閾値
  位置が動く）は GPU 側フェーズ（P0／P4／P5）に依存しないため、
  glibc mmap しきい値がホスト側の主因であること自体はこの 2 つの実験
  のみで確定できる。**§4.2（P4 vs P5 の対照。D2H 転送先の未タッチ有無
  が原因という「発症箇所」の特定根拠）は、冒頭追記のとおり
  `synchronize` 追加前のテストで得た値であり修正後の GB10 実機再実測が
  未反映のため、この対照自体は参考値・再実測待ちとして扱う**
  （§6 結論 3 も同様）。`clone_dtoh` の
  宛先 `Vec` が `Vec::with_capacity` + `set_len`（未タッチページ。
  `cudarc-0.19.8/src/driver/safe/core.rs`）で確保されるため、32 MiB
  以上では glibc が mmap 経由でゼロ埋めページを割り当て、初回アクセス
  （`memcpy_dtoh` の書き込み）時のマイナーページフォルトコストが計測に
  混入する。§4.4 の「降順パスでのみ発生する追加スパイク」は H-A の
  枠内でも未確定の副次現象（ヒープ断片化・mmap/munmap のカーネル側
  コストの確率的変動）として残る。
- **H-B（デバイス側・`cuMemAllocAsync` プール／unified memory）: 棄却
  （未確定・再実測待ち）**。§4.3 で P1（`stream.alloc` のみ）・P2
  （`alloc_zeros`）とも 8〜64 MiB 全域でサイズに対しほぼフラット
  （P1: 常に 0.0009 ms・P2: 常に 0.003〜0.004 ms）であり、32 MiB での
  不連続は皆無だった。ただし冒頭追記のとおり、この P1／P2 計測は
  `synchronize` を挟まず enqueue 直後に打ち切っていたため、`cuMemAllocAsync`
  ／memset が非同期 enqueue で返るだけなら確保完了時間を計測できて
  おらず、このフラットな値だけでは「デバイス側確保は外れ値の原因では
  ない」と確定できない。`synchronize` 追加後のテストコードでの GB10
  実機再実測が完了するまで、H-B の棄却判断は保留する（冒頭追記参照）。
- **H-C（H2D 側・ページャブル転送のステージング）: 棄却**。§4.3 で P3
  （host_src を計測外で事前確保・書き込み済みにした H2D 単体）は
  8〜64 MiB 全域で完全に線形（帯域律速）であり、32 MiB での不連続は
  皆無だった。

P0（参照計測）の値は P1〜P4 の和とおおむね整合する（例: size=32 asc、
P0 median 19.4 ms ≈ P3 0.576 + P4 17.96 + α〈P1／P2 は無視できる程度〉）。
#1123 の合算計測（dim4096・約 261〜263 ms）に近い値は本イシューの
スイープでは 64 MiB（片側）までしか到達していないため直接再現していない
が、§4.4 の 24 MiB desc run_idx=1（p4 median 240.35 ms）で同オーダーの
値を確認しており、外れ値の根本メカニズムは同一（未タッチ D2H 宛先 ×
glibc アロケータの確率的コスト増）と判断できる。

## 6. 結論

1. **閾値サイズは 32 MiB で、両走査順（昇順・降順）・GPU 非関与の
   P6 で再現する**（§4.1）。これは glibc 64-bit Linux の
   `M_MMAP_THRESHOLD` 動的既定上限（32 MiB）と一致し、
   `MALLOC_MMAP_THRESHOLD_` を変更すると閾値位置も追従して変化する
   ことを確認した（§4.6）。P0・P4 での同一閾値の再現（§4.2）は
   `synchronize` 追加前のテストで得た値であり、修正後コードでの
   GB10 実機再実測が未反映のため参考値・再実測待ちとして扱う
   （冒頭追記参照）。
2. **閾値は単体バッファサイズに対して働き、合計転送サイズには働かない
   （未確定・再実測待ち）**（§4.5。16 MiB×3・24 MiB×2〈いずれも合計
   48 MiB〉は無症状、単体 32 MiB 以上で発症）。この結論は
   `synchronize` 追加前のテストで得られた値であり、かつ元の §4.5 は
   H2D（`clone_htod`）のみの比較で D2H を含んでいなかった（冒頭追記の
   不備 (2)）。D2H 側の対照実験はテストコードへ追加済みだが、本 PR の
   環境（CUDA 実機なし）では GB10 実機再実測を実施できていないため、
   「合計転送サイズには働かない」という結論は D2H 側について未確認の
   まま残っている。修正後コードでの GB10 実機再実測後に確定表現へ
   復元する（冒頭追記参照）。
3. **発症箇所は D2H 転送の「宛先ホスト `Vec` が未タッチである」ことに
   限定される可能性が高い**（§4.3。デバイス側確保〈`cuMemAllocAsync`〉・
   H2D 転送はいずれも閾値を持たない）。**P4 vs P5 の対照（§4.2）を
   根拠とする「D2H 側に限定される」という確定表現は、`synchronize`
   追加前のテストで得た値のため保留し、修正後コードでの GB10 実機
   再実測後に復元する**（冒頭追記参照）。
4. **追加で、32 MiB 以上のフェーズを経由した直後の降順走査でのみ、
   32 MiB 未満のサイズでも確率的に約 240 ms 規模のスパイクが発生する
   場合がある**（§4.4。3 回に 1 回。原因は未確定・H-A の枠内の副次
   現象と推定）。順序依存の存在自体は確認したが、発生条件の完全な
   特定（何が引き金か）は本イシューのスコープを超える（§7 引き継ぎ）。
5. **1 回目 vs 2 回目以降**: cold（プロセス内で初めてそのフェーズを
   呼ぶ 1 回目）は warm（20 回 warmup 後の中央値）よりおおむね高いが、
   32 MiB 未満では数倍〜十数倍程度の差に留まり（例: size=8 の P0 で
   cold 17.7 ms・warm median 0.458 ms）、32 MiB 以上ではむしろ cold と
   warm の差が縮まる（同じ mmap しきい値効果がほぼ毎回発生するため）。
   #1123 の「1 回目 0.0185 s・2 回目 0.260 s」の逆転パターン（2 回目の
   方が遅い）は本イシューの cold/warm 軸だけでは説明されず、§4.4 の
   確率的スパイクと同根と推定される。
