- OS: Linux aarch64
- NVIDIA driver・CUDA (nvcc) は #1148 時点と同じ環境（本計測は CPU 経路の
  みで CUDA feature を持つ `bench-candle` のビルドにのみ `nvcc` が必要）
- **`thread_limit_report()` 生値**（`--nocapture`。`thread_limit_report-dgx.log`）:
  `ThreadLimitReport { current: 20, detected_big_cores: Some(1), env_override: false, effective: 1 }`
  （BIG_CORE_LIMIT_ENABLED=true 時点）
- **重要な診断結果**: `/sys/devices/system/cpu/cpu<N>/cpu_capacity` の実測値は
  `lscpu` が報告する「X925 ×10 + A725 ×10」の 2 群構成と一致しない、5 段階
  の非一様な分布だった（cpu0-4=718・cpu5-9=997・cpu10-14=731・cpu15-18=1017・
  cpu19=1024。DVFS ブースト状態等を反映した容量値と見られ、単純な big/little
  2 分類ではない）。`thread_limit.rs::big_cores_from_capacities` は「最大値と
  一致するコア数」を大コア数とするため、この分布では cpu19 の 1 個のみを
  「大コア」と誤検出し、`effective_num_threads` が実質シングルスレッド
  （`effective=1`）へ縮退した。これが #1364 の on/off 比較で DGX が甚大な
  後退を示した直接原因である
- 負荷状態: on 腕開始前 `load average: 0.06, 0.02, 0.00`（ほぼ専有）。
  off 腕（ビルドキャッシュ再利用のため高速）完了時 `load average: 6.64, 3.26,

## 採否

**REJECT（不採用）**。決定規則（両実機・全判定可能セルで reuse の ratio<=1.05
を要求）に対し、DGX の reuse 全セルが 1.19〜4.34 倍の重大な後退を示した。
M4 Max 単独では 0.80〜0.91 倍の改善が確認できたが、DGX の後退が上記診断結果
（`cpu_capacity` 分布の誤検出による実質シングルスレッド化）という明確な原因を
伴う重大な後退であるため、両実機総合で不採用と判断した。
`crates/backend-cpu/src/thread_limit.rs::BIG_CORE_LIMIT_ENABLED` を `false`
へ差し戻し済み（本イシューのコミット。#1362 の受入条件を充足）。

Linux 側の大コア検出手段（`cpu_capacity` 以外の指標。例: `/sys/devices/system/
cpu/cpu*/topology/*` の `capacity_dmips_mhz` や `lscpu` のモデル名グルーピング
等）の見直しはスコープ外事項として PR 本文に記録する（ユーザー承認前提の
Issue 起票は本エージェントでは行わない）。
