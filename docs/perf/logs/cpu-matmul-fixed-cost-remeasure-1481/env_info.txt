## 事前登録した判定規則（計測開始前にここへ転記。転記時刻 2026-09-09T12:14:02Z）

`docs/perf/cpu-gemm-candle-gate-remeasurement.md` §20.1（規則 1〜3・5）・
§20.1a（規則 4 改定版）から、計測前に一字一句このファイルへ転記する。
以後、計測結果を見て文言・数値を変更しない。

1. **checksum**: 全セルで off/on 完全一致（`compare_gemm_ab.py` の複合
   判定 pass かつ `==` 列一致）。不一致なら判定不能。
2. **DGX N=2048 reuse（決定セル）**: Layer B の `alloc_c` 中央値が
   削減され、かつ `ops_gemm` 中央値の on/off 比 ≤ 1.00。Layer A
   （`run_gemm_gate_cpu.sh`）の 2048/reuse の on/off 比 ≤ 1.05（非後退）。
3. **対照セル**: 両実機の N=512/1024 の reuse/fresh すべてで on/off 比
   ≤ 1.05。
4. **規則 4（改定版・§20.1a）**: 各セルの candle 比 on/off 比
   （`on 腕の candle 比 / off 腕の candle 比`）が `1/1.05 ≈ 0.9524` 以上
   であること（規則 2・3・5 と同じ `±5%` 慣例許容幅を、比の比という
   間接指標に対して逆数側〈悪化方向〉のみへ適用する片側検査）。
   対象は両実機 × N=512/1024/2048 の 6 セル全部。
5. **M4 Max N=2048**: on/off 比 > 1.05 で 5 run 符号一貫の後退なら
   macOS では有効化しない（#1299 スモークの再確認）。

結線の場合分け: (a) DGX が規則 1〜4 を満たし M4 Max が規則 5 で後退 →
ADOPT（Linux 限定 cfg gating）。(b) DGX で削減されない・後退する →
REJECT（コード無変更）。(c) 両実機とも全規則を満たす → 無条件
`2 << 20`。いずれか不成立（(a)(c) いずれにも該当しない）→ REJECT。
専有ゲート不成立で片実機が欠ける → **undetermined**（1 回だけ記録して
終了。ユーザー承認 2026-09-09・memory `handover-approvals-2026-09-09`）。

**規則を計測後に緩和・読み替えない**（本イシューの存在理由そのもの。
PR #1448 の codex-review 指摘の是正）。数値判定は `judge_rules.py` に
ハードコードし、機械的に適用する。

## 実行結果サマリ（2026-09-09 実施）

対象コミット: 54cb14057dbf30cc77a3d77c0d1b37caf348f75c

**規則 1（checksum）**: 両実機・全 6 セルで `compare_gemm_ab.py --device
cpu --sizes gate` の checksum 列が「完全一致」（`compare_gemm_ab-dgx.md`・
`compare_gemm_ab-m4max.md`）。`parity_fail_count` は全 120 行（両実機×
off/on×5run×6cell）で 0。**満たす**。

**規則 2（DGX N=2048 決定セル）**: Layer A 2048/reuse on/off 比 0.7090
（≤1.05・満たす）だが、Layer B `alloc_c` on/off 比 **2.1199**（削減ではなく
約 2.1 倍に増加。§20.3 の #1301 実測〈0.5166・約 48% 削減〉とは逆符号）。
`alloc_c` 削減の条件を満たさないため**規則 2 は不成立**（`ops_gemm` 比
0.8012 は ≤1.00 を満たすが、規則は「`alloc_c` 中央値が削減され、かつ
`ops_gemm` ≤1.00」の AND 条件であり alloc_c が削減されていない時点で
不成立）。

**判定コードの計測後修正について（透明性のための明記）**: `judge_rules.py`
初版は §20.1 規則 2 の文言（「`alloc_c` 中央値が削減され、かつ `ops_gemm`
≤1.00」）のうち `alloc_c` 削減条件をコードへ反映し忘れており、
`layer_a`・`ops_gemm` の 2 条件のみで判定していた。この状態で一度
`judge.md` を生成したところ規則 2 は「満たす」と出力されたが、これは
事前登録文言との不一致（バグ）によるものであり、`alloc_c比=2.1199`
という出力自体は最初から表示されていた。バグを発見し `alloc_c < 1.0`
条件を追加（事前登録文言への整合のみ・**厳格化方向の修正**であり
緩和ではない）してから `judge.md` を再生成し、規則 2 を「不成立」へ
訂正した。修正前後で規則 3・4 は独立に不成立のままのため、
**verdict=REJECT は修正前後で不変**（本コミットに含まれる `judge.md`・
`judge_rules.py` は修正後の版のみで、修正前の出力は保存していない）。

**規則 3（対照セル）**: 両実機 N=512/1024 の fresh/reuse 全 8 セル中
3 セルが不成立（DGX 1024/fresh 1.0549・M4Max 512/fresh 1.0576・M4Max
512/reuse 1.0780。いずれも 1.05 をわずかに超過）。**不成立**。

**規則 4（改定版）**: 両実機×N=512/1024/2048 の 6 セル中 5 セルは満たすが、
M4Max N=512 が candle 比 on/off 0.9060（<0.9524）で**不成立**。

**規則 5（M4Max N=2048 後退判定）**: Layer A on/off 比 1.0212（≤1.05）
のため後退なし・発火せず。

**verdict = REJECT**（`judge_rules.py` 出力 `judge.md` 参照。規則 2・3・4
のいずれも不成立セルを含むため、§20.1 の場合分け (a)〜(c) いずれにも
該当しない）。**規則は計測後に一切緩和・読み替えていない**（事前登録
版のまま `judge_rules.py` にハードコードして機械適用）。本番既定
`GEMM_OUTPUT_PARALLEL_ZERO_MIN_ELEMS = usize::MAX`（無効化）は変更しない
（`crates/**` は本コミットで無変更）。

なお #1301（§20.3）の実測と本イシューの実測は方向性が一部逆転している
（DGX alloc_c は削減→増加、DGX/M4Max の一部対照セルは非後退→僅かな
後退）。事実として、DGX N=2048 off 腕（=usize::MAX・変更なしの本番
既定経路）の `alloc_c` 中央値自体が #1301〈145639d 時点。3.2554 ms〉
から本イシュー〈54cb1405 時点。0.1969 ms〉で約 16 倍縮小しており、
§16（`docs/perf/cpu-gemm-candle-gate-remeasurement.md`）が指摘した
「DGX N=2048 の `alloc_c` 異常（2.8〜3.0 ms）」はこの HEAD では観測
されない（原因は本イシューでは特定しない。事実の記録のみ）。両実機
とも共有負荷下（M4Max は他 worktree 並走・DGX も load average が
計測中 6〜12 まで上昇する区間があった）での 1 セッション限りの計測で
あり、本イシューは「事前登録した規則を機械的に適用して ADOPT/REJECT
を確定する」ことが目的であるため、この方向性の違いの原因分析（真の
後退か計測ノイズか、alloc_c ベースライン自体の縮小によるものか）
自体はスコープ外として記録するに留める。
