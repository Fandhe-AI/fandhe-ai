  （crates・scripts/bench・Cargo.toml・Cargo.lock・rust-toolchain.toml の全ファイルの「SHA-256  相対パス」一覧を

3. 計測手順
  ラウンド数は PARAMS の rounds（既定 5）。各ラウンドの前にゲートを通す。
    Mac mini: hw-lock を取得し、load1 < 3.0 を最大 30 分待つ。
    GB10: compute プロセス 0 の専有を 30 秒間隔で最大 30 分待つ。
  ゲート不通過は gate.txt に TIMEOUT と記録し、そのラウンドを正式系列から外す（status=partial・確度は常に低・表題は「参考」）。
  ラウンド内の腕の順序: 奇数 round は Rust 腕（bench-fandhe の train／infer × fresh／reuse の 4 本 → cpu_jobgrid_bench threads）→ Python 腕（bench_py.py pytorch の train／infer → opp_kernel_torch_diag measure --shapes mlp --arm base --device cpu）、偶数 round は Python 腕 → Rust 腕。bench_py.py の sha256 9fd2c08f37d66b5bb41ececab8a5b3daaa36b55609770502ed3b35ae2ce2409b を照合し、torch は 0.14.0 計測と同じ 2.14.0（違えば停止）。record_only として bench-fandhe train --phases --mode reuse・infer --phases を取る（分類には使わない）。起動は run_round.sh、変換は to_values_4146.py。計測中にビルド・集計・転送を並走させない。
  run の差し替え・追加・除外・上書きは禁止。再実行は別ラベルとし、旧系列を残す。
  到達不能な量は unavailable と記録し、推定値で埋めない（values.tsv にも書かない。式が計測できないなら RULE を改訂して式を外す）。
  保存物: round{i}/{gate.txt, values.tsv, raw/}・env/。ハーネス固有の出力から values.tsv への変換は計測する issue が行い、変換手順を README に残す。

4. 診断式（docs/perf/loss-attribution-matrix.md §10.1 から転記。単位は ms）
  入力量: fandhe_window・fandhe_fresh_window・opp_window・fandhe_pure_kernel・opp_pure_kernel
  F1 = opp_window ÷ (fandhe_window − fandhe_pure_kernel + opp_pure_kernel)
       純カーネルの時計タグ（clock 列）を両側で揃える。揃わなければ F1 は比較不能とし、境界を併記する。
  F2 = opp_window ÷ fandhe_fresh_window
  観測比 = opp_window ÷ fandhe_window（スコアボードの比との整合確認用）
  1 以上は「相手の構成を再現すれば届く」を意味する。診断であり目標値ではない。
  純カーネルの境界（#4146 で追記）: GEMM のみ。ReLU・MSE・SGD・readout は両側とも含まない。
    学習は l1_fwd・l2_fwd・l2_dw・l2_dx・l1_dw の 5 形状（l1_dx は含めない。fandhe-ai の常駐チェーンも PyTorch〈入力に勾配を求めない〉も実行しないため）。推論は l1_fwd・l2_fwd。
    時計タグは両側 wall（fandhe-ai は cpu_jobgrid_bench の median_secs、PyTorch は opp_kernel_torch_diag の mm_pure。単発 GEMM を温めた状態で測った値の和で、step 内の状態とは一致しない。F1 の注意）。
    fandhe_window は reuse（常駐チェーン。第 1 層の dX を計算しない）、fandhe_fresh_window は fresh（run_train。L1 の dX を計算する）。
    kernel_owner=hardware の根拠: PyTorch CPU の GEMM は閉源の Accelerate で、REQ-1 により fandhe-ai は使わない（unreached_0140.tsv の M-CPU-G256 を「ハードの上限」とする先例に揃える）。測る前の宣言で、BLAS 経路が違っても動かさない。
    PyTorch CPU の MLP 経路の精密な切り分けは #4148 の担当。値が食い違えば RULE.v2.txt で改訂する。

5. 判定の分類先と規則（優先順位つき。aggregate_diag.py の classify と同一）
  分類先: 自分たちの制約／ハードの上限／計測窓の定義／分類保留
  (1) formulas に F2 があり、F2 の run 間中央値が reach_threshold 以上なら「計測窓の定義」。
  (2) そうでなく F1 があり、時計が揃っていて、F1 の run 間中央値が reach_threshold 以上なら、
      kernel_owner=hardware は「ハードの上限」、kernel_owner=constraint は「自分たちの制約」。
      kernel_owner は測る前に宣言する（hardware: 閉源ライブラリ・OS・ハードが決める。
      constraint: REQ-1・REQ-8・既定精度が決める。matrix §10.5 の定義）。事後に動かさない。
  (3) それ以外は「分類保留」。理由欄に「どれも届かない（残差は固定費など別区間。別診断へ）」または「F1 の時計不一致」を書く。
  確度:
    高: 全ラウンドがゲート PASS（status=formal）かつ、判定に使った式の run 別値がすべて閾値の同じ側
        （最小 > 閾値、または最大 < 閾値。境界ちょうどはまたぐ扱い）かつ時計が揃っている。
    低: 上記以外。理由欄の先頭に「確度低」を付ける。
  ドリフト: 観測比の中央値が PARAMS の scoreboard_ratio から 10% を超えて乖離したら記録する（判定は変えない）。
