# ---- 判定（判定契約は既存テストのコードが定める。ここでは変えない）----
pass: 各テストごとに exit 0 かつ「running 1 test」かつ「test result: ok. 1 passed; 0 failed」
fail: 1 件以上の失敗（パニックを含む）
undetermined: ノードに届かない、ビルドできない、timeout（exit 124）、--list の不一致、実機ロックの取得不能・喪失、自己検査の失敗、
  tree_check の不一致、build_freshness の不成立、0 本実行。pass として扱わない
stop: 1 本目が fail・undetermined なら 2 本目は実行せず、記録して止まる
completion: 2 本とも pass で、回収物の確認（rev_stamp・script_sha256・ソースの指紋・build_freshness）も成立し、かつもう一方のノード（Metal）の計測 PR がすでに main にマージされていて pass のときだけ #4053 を Closes する。
  それ以外は Refs #4053
output_on_pass: assert_parity_f64 は pass のとき何も出力しないので、量ごとの fail_count・max_abs_diff などはログに出ない。これは fail にも undetermined にも数えない。
  結果はテスト単位の pass と書き、量ごとの数値は埋めない。assert_parity_f64 は fail_count が 0 でなければ panic するので、テストの pass は対象の量の fail_count が 0 であることを意味する

# ---- 事前ビルドと実行（各本ごとに、スクリプトが順に行う）----
build_then_run:
  0) 送信側で上の hw_lock の確認とロックの取得を行う。1 本目はこのあと転送と照合を行ってからスクリプトを起動する。2 本目は転送せず起動する
  1) 開始前に pgrep で他の cargo／rustc が無いことを確かめる。tree_check の不一致でも停止する
  2) build_freshness の clean の後、cargo test -p fandhe-ai --test <テストターゲット> --no-run でビルドを終える（判定外。build.log）
  3) cargo test -p fandhe-ai --test <テストターゲット> -- --ignored --exact --list <テスト名> の出力で、": test" で終わる行がちょうど 1 件であることを確かめる（list_1.log）
  4) build_freshness の time_check を行い、次を 1 回だけ別プロセスで実行する:
     timeout 900 cargo test -p fandhe-ai --test <テストターゲット> -- --ignored --exact --nocapture --test-threads=1 <テスト名>
external_timeout: timeout 900。ハングを pass にしない。timeout は undetermined

# ---- 記録 ----
record: 各本の出力先に、実行ログ全文（--nocapture）を <LOG_BASE>_1.log（末尾に rc=）、終了コードを exit_code_1、判定を summary.tsv に書く。
  LOG_BASE は f64_create_graph_cuda と f64_jvp_family_cuda。回収は docs/perf/logs/f64-gpu-parity-4053-cuda/create_graph/ と同 jvp/ へ分ける。
  summary.tsv の verdict は exit code と test result 行で決まり、非 0 終了はすべて fail と書かれる。timeout と不成立の区別は上の定義でログから決め、README に書く
masking: ホスト名・ユーザー名・ホームのパスを <cuda-node>／<user>／<home> へ置換する（前後が識別子文字でない場合のみ）。
  漏れたら記録を捨てて、所有者へ報告する。回収ログは手で編集しない。回収後に送信側でも PR 差分全体をユーザー名・/home/・内部ドメイン・SSH 別名で grep し、0 件であることを確かめる
integrity: 各本の保存ファイル群の SHA256SUMS を作り、env_info.txt の script_sha256・rev_stamp と合わせて実行と提出物の対応を検証する

# ---- fail の扱い ----
fail_handling: fail・undetermined が出ても tolerance・baseline・閾値・判定方式・判定の helper・入力・テストコード・この RULE を変えない。再実行で置き換えない。
  panic メッセージのテスト名・量・fail_count・max_abs_diff・max_rel_err をそのまま引用して事実を記録し、
  README と PR に「要対応」と書き、所有者へ報告して止まる。原因を推測で結論づけない。起票と baseline 化は所有者の承認を得てから行う
build_freshness:
  背景: 共有 CARGO_TARGET_DIR の workspace メンバー成果物が前の回のものの再利用になりうる。条件と対策は
    docs/real-hardware-shared-target-reuse-decision.md、手順は docs/real-hardware-verification-env.md §4.11
  clean: 各本の build_then_run の 2) の前に、cargo metadata --no-deps の全メンバーへ cargo clean -p <名前> を実行する（--release なしなので dev プロファイル）。crates.io の依存は消さない
  time_check: 各本のビルド後、テストバイナリと全メンバーの lib 成果物（target/debug/deps の lib<名前>-*.rlib・.rmeta。facade 自身の libfandhe_ai-* を含む）の
    更新時刻が、その本のロック取得（ノード上の owner ファイルの mtime）より秒単位で厳密に後であること。結果を各本の build_artifacts.txt に保存する
  undetermined: 古い成果物が 1 つでもある、ロックと同じ秒、必須 lib の欠落、テストバイナリの欠落、実行したバイナリが確かめたものと違う。テストを実行しない
  script: 同ディレクトリの 2 本のスクリプト（雛形 docs/perf/logs/hw-parity-run-template/run_parity_template.sh の R4・R5 をそのまま含む）
