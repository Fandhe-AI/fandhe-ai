本規則は計測より前に固定する。事後に緩めない。変更が要る場合は別名の RULE を計測前に再登録する。
本件は GB10 の train CUDA 専用の A/B である。#1350（更新区間だけの capture。中立判定）は範囲が異なる別条件であり、本件はその判定を覆さない。
正式な 6 フレームワーク同席計測は #3273 が担当する。

[対象]
- runner = 本規則を含むコミット（フル SHA は .rev-stamp 1 行目と env_info の rev_stamp_head_runner）。on／off の両腕は同じバイナリ・同じコミット。腕の差は環境変数だけ。
- facade = 同じツリーの crates/facade への [patch.crates-io.fandhe-ai] path patch（--config 引数のみ。Cargo.toml／Cargo.lock へはコミットしない）。
- 計測専用パッチ docs/perf/logs/resident-chain-ab-3257/bench-resident-chain.patch（sha256 は下記）を runner ツリーにだけ適用する。env_info の patch_sha256 と judge が突合する。
  patch_sha256: 92d0a8d446790feedfb0c3392c76c3641ac7977a1a604e26f68f5c811ac3a819

[腕]
- off: FANDHE_AI_CUDA_GRAPH_TRAIN・FANDHE_AI_CUDA_GRAPH_STEP・FANDHE_AI_CUDA_GRAPH_INFER がすべて未設定（継承環境に存在すればランナーが停止する）。
- on: FANDHE_AI_CUDA_GRAPH_TRAIN=1 だけ（他の 2 つは未設定）。
- 相手: candle・torch（PyTorch 2.14.0+cu130）。判定には使わない。
- TF32 OFF（--tf32 なし）・--graph なし・size=64。

[セル（すべて GB10 の train CUDA）]
- 判定セル chain（--mode chain）: capture が届く唯一の経路（DeviceParamStore::train_step_device_chain）。
- 対照セル reuse・fresh: bench-fandhe の経路は forward_resident → backward_device_param_store → sgd_step_device_tracked でチェーンに届かない。
  on で変わるのは created stream 化とイベント追跡の無効化（train_graph_stream_requested() の OR）だけ。事前に「stream 変更のみの効果」と帰属する。
  既定を反転すると全 CUDA 利用者の stream が変わる（設計 §8.5）ため、その副作用の非後退を見る役目。
- セルは 6 つ（{chain, reuse, fresh} × {off, on}）。各セル 5 run。

[手順]
- 5 round 固定（AB_ROUNDS が 5 以外なら拒否）。プロセスは独立起動。run の差し替え・追加起動・セル除外はしない。同じラベルの既存出力があれば停止。RAYON_NUM_THREADS は unset。
- round ごとに 8 腕の起動順を回転する。腕の基準順 L = [chain-off, chain-on, reuse-off, reuse-on, fresh-off, fresh-on, candle, torch]。round r は L の位置 3*(r-1) mod 8 から巡回する。
  r1: chain-off chain-on reuse-off reuse-on fresh-off fresh-on candle torch
  r2: reuse-on fresh-off fresh-on candle torch chain-off chain-on reuse-off
  r3: candle torch chain-off chain-on reuse-off reuse-on fresh-off fresh-on
  r4: chain-on reuse-off reuse-on fresh-off fresh-on candle torch chain-off
  r5: fresh-off fresh-on candle torch chain-off chain-on reuse-off reuse-on
- reuse・chain の fandhe 腕には BENCH_PARAM_DIGEST=1 を付ける。
- 全ビルド（bench と前提ゲートのテストバイナリ）を計測の前に済ませる。計測中のビルド並走禁止（開発機・ノードとも）。

[専有ゲート]
- load1 < 1.0 かつ GPU 使用率 0% を 3 サンプル連続。30 秒間隔・最大 30 分。round ごとに通す。不通過 round を含む系列は undetermined。

[機体の同定]
- uname -m = aarch64。nvidia-smi の GPU 名に GB10 を含む。env_info に記録する。

[前提ゲート（計測と同じ HEAD・GB10・既定 feature・--release。省略不可。SKIP・未実行は不合格）]
- R0（非後退。環境変数なし／各 opt-in なし）: train_step_chain_diag_tests_3252（3 passed）・graph_capture_real_device（2 passed）・graph_capture_real_device_optin_off（1 passed）。
- R1（結線の証明。bench からは train_graph_stats を観測できないため必須。FANDHE_AI_CUDA_GRAPH_TRAIN=1）:
  facade の cuda_graph_train_step_bit_identity::in_process_capture_matches_plain_chain_bit_exact（--exact・1 passed。組み合わせごとに captured 1・replayed 8・fallbacks 0 をテスト内で表明）と、
  backend-cuda の train_step_graph_diag_tests_3260（--test-threads=1・8 passed）。
- R2（2 プロセスの bit 一致）: dump_bits_for_two_process_diff を環境変数なしと =1 で 1 回ずつ実行し、BITS 行を比較して差が空であること。BITS 行が 0 なら不合格。
- 各ログに rc= 行（終了コード）を残す。

[hard 条件（判定より先）]
- 各セルで off／on の checksum（最終 loss）が全 run で完全一致。
- chain・reuse は PARAM_DIGEST も全 run・両腕で同値（欠落は不一致として扱う）。
- 不一致は REJECT（正しさの失敗）。相手の checksum は記録するだけで判定しない。

[比]
- ratio = median(on 5 run の median_s) / median(off 5 run の median_s)。ratio_r = on_r / off_r（JSONL の行順 = round 順）。
- 相手軸（参考・判定外）: 同一 round 内の有効な相手最速（candle・torch の小さい方）÷ fandhe 5 round 中央値を off・on それぞれで出す。

[判定]（#1350 の「ratio <= 0.95・5/5 符号一貫」と #2115 の「全セル <= 1.00」を合わせる）
- ADOPT（すべて満たす）:
  1. 専有ゲートを全 round で通過。
  2. R0〜R2 がすべて合格。
  3. hard 条件をすべて満たす。
  4. chain で ratio <= 0.95 かつ 5/5 round で ratio_r < 1.00。
  5. reuse・fresh の ratio <= 1.00（既定反転で全利用者に及ぶ stream 変更の非後退）。
- REJECT（いずれか）: chain の ratio > 1.00／reuse・fresh のどちらかの ratio > 1.00／hard 条件の不一致／R1 または R2 の失敗（結線の不成立・bit 不一致）。
- undetermined（いずれか）: 専有ゲートの不通過／run 数不足・欠測セル／R0〜R2 の未実行／GB10 以外／env_info・RULE sha・パッチ sha の不一致／ADOPT にも REJECT にも当たらない（例: chain が 0.95 < ratio <= 1.00、または 5/5 に満たない）。
- 判定の優先順: 入力不正 → undetermined 要因 → hard 条件・前提ゲートの失敗（REJECT）→ 比。

[判定後の扱い]
- ADOPT でも TRAIN_GRAPH_DEFAULT_ENABLED は本件で変えない。既定の反転は設計 §8.6 により所有者判断で、全 CUDA 利用者の stream・イベント追跡の変更、lr スケジューラ下で 3 step 後に既存チェーンへ戻る点を含む影響評価と別 PR を要する。
- REJECT・undetermined も正当な結果として記録する。tolerance・baseline・依存ピンは変更しない。

[事前表明する仮説（推定・合格ラインではない）]
- chain は launch 固定費の削減で改善する見込み。#3257 の chain は 0.1343 ms（candle 比 2.02x）。到達目安 0.10〜0.15 ms は根拠の薄い推定。
- fresh・reuse は中立か、わずかな改善（#1350 では stream 変更単独が改善方向）。

[限界]
- bench 自体からは capture が replay されたかを観測できない。R1 が結線を示すが、R1 の形状（784-256-10・batch 64 ほか）は bench の形状と同一ではない。
- checksum の一致は bit 同一性の証明ではない。PARAM_DIGEST と R2 で補う。

[ドリフトガード]
- ゲート定数（load1 閾値 1.0・GPU 使用率 3 サンプル）のドリフトガードテストは最初から除外を明記する（計測条件の変更ではないため）。

[対象外]
- 既定の反転、(B) cuGraphExecUpdate（新規 unsafe・未承認）、x／y の staging 方式（設計 §8.8.2 案 (i)）、infer・CPU・Metal セル、#3273、bench から capture の stats を観測する手段（framework-compare の依存 allowlist 変更が要る）。
