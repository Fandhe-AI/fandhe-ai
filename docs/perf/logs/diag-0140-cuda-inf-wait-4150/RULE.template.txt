3. 計測手順
  ラウンド数は PARAMS の rounds（5）。各ラウンドの前に実機ロックを取得し、compute プロセス 0 件・GPU 使用率 0 が 3 サンプル連続・
  load1 < 1.0 を 30 秒間隔で最大 30 分待つ。不通過は gate.txt に TIMEOUT／INVALID と記録し、そのラウンドを正式系列から外す
  （TIMEOUT／INVALID を 1 件でも含む系列は status=partial・表題は「参考」・確度は書かない。全 round PASS のときだけ status=complete）。同じ GB10 を #4147・#4149 の実測も使うため、実機ロックで直列化し並走させない。
  1 round = 1 プロセス（example の warmup と計測反復は PARAMS の warmup・iters）。反復ごとに P・E・PR・ER・I の順を巡回させ、F は各反復の末尾に測る。
  nsys 補助（nsys_aux_4150.sh）は全 round の後に 1 回、record_only。時間値は判定に使わない。
  計測中にビルド・集計・転送を並走させない。run の差し替え・追加・除外・上書きは禁止。再実行は別ラベルとし旧系列を残す。
  全反復で出力 bit 一致（example が assert）。checksum は round 間で一致しなければ集計が止まる。
  到達不能な量（nsys 不通など）は unavailable と記録し、推定値で埋めない。

4. 腕と区間の定義（単位 µs）
  チェーン（P・E）: 常駐 w・bias を upload、入力 H2D、L1 = 784→256＋bias＋ReLU 融合、L2 = 256→10＋bias、download。L1 発行直後に入力を、L2 発行直後に中間を drop。
    呼び出し列は #3189 と同じ（層ごとに確保経路 linear_forward_device）。0.14.0 の本番 predict_device_chain は 2 回目以降に層出力を
    into 経路で再利用する（#3205）ため、層ごとの出力確保・ゼロ初期化・drop を含む点で本番と異なる。
  本番列（PR・ER）: 入力は区間外で 1 回だけ upload した常駐入力（ResidentInput 相当。drop しない）、層出力 h・y は区間外で 1 回だけ
    確保＋ゼロ初期化して全反復で使い回す（ChainScratch の 2 回目以降相当。PR と ER で共有）。区間内は L1 into 発行・L2 into 発行・download のみ
    （区間内に確保・ゼロ初期化・H2D・drop を含まない）。L1／L2 は I 腕と同じ融合カーネルの into 経路（linear_forward_device_into_tracked）。
    本番からの省略: store 層の try_lock・key 照合・checked_resident_buffer・poison 検査、facade の tape・snapshot・steps の解決、初回呼び出しのプローブ、
    Graph capture 経路（常駐入力では通らない）。ホスト入力版 predict_device_chain は本番列に入力の確保＋H2D と L1 発行後の入力 drop が加わった形で、未計測。
  P: host Instant のみ（h2d_upload・l1_issue・l2_issue・download・download_again・kernel_wait_derived = download − download_again・total）。
    h2d_upload は入力の device 確保＋H2D。l1_issue／l2_issue は検査・出力の確保＋ゼロ初期化（alloc_zeroed）の発行・カーネル発行・前段の drop。
    download／download_again は D2H＋同期（host 側 Tensor の確保を含む）。
  PR: host Instant のみ（l1_issue・l2_issue・download・download_again・kernel_wait_derived = download − download_again・total = l1_issue + l2_issue + download）。
    download／download_again は D2H＋同期（host 側 Tensor の確保を含む）。
  ER: PR と同じ列に event 3 本（e0=L1 発行前、e1=L1 発行直後、e2=L2 発行直後）。l1_span=e0→e1、l2_span=e1→e2、chain_gpu=e0→e2、
    download と l1_issue／l2_issue は host 時間。GPU 側の幅は層出力のゼロ初期化を含まず、host の発行待ちによる GPU の空きだけを含む。
  E: P と同じチェーンに event 4 本（e0=upload 前、e1=upload 後、e2=L1 発行直後、e3=L2 発行直後）。up_gpu=e0→e1、l1_span=e1→e2、l2_span=e2→e3、chain_gpu=e1→e3。
    GPU 側の幅は、層出力のゼロ初期化と、host が確保・発行している間の GPU の空きを含む。
  I: drain 後に event 対で、P・E と同じ融合カーネルを into 経路（linear_forward_device_into_tracked。区間外で事前確保した出力へ書く）で
    層ごとに 1 回挟む（l1_iso・l2_iso）。出力の確保・ゼロ初期化・入力の H2D・event 生成は区間外。l1_host／l2_host は同じ呼び出しの host 時間。
  F: sync_idle・launch_floor_1x1・tiny_roundtrip・event_record_pair。各区間の前に drain（synchronize）してキューを空にする。
    1x1 カーネルは I と同じく事前確保した出力への into 経路で、区間内に device 側の確保・ゼロ初期化を含まない。
    #4149 の cuda_fixed と区間定義が同じもの: sync_idle（アイドルでの synchronize）、tiny_roundtrip（1 要素 kernel〈1x1 linear〉の発行＋
    1 要素 D2H＋同期を 1 区間で計る。D2H は host 側 Tensor の確保を含む）、event_record_pair（event 記録 2 本だけの host 時間）。
    異なるもの: launch_floor_1x1 は 1x1 into 1 回の発行時間で、#4149 の launch_floor_add
    （1 要素 add を 100 回 enqueue した 1 回あたり）とは演算も回数も違う。対応表では参考として並べるだけにする。
  stream は internal-diagnostics 下の Legacy（NULL）stream であることを example が前提検査する。

5. 導出式（内訳であり合否判定ではない。round ごとに腕別反復中央値から計算し、round 間の中央値と最小〜最大を出す）
  以下の量は系列ごと（seq3189＝P・E、prod0140＝PR・ER）に計算する。E_sum と F 腕は共通（common）。分類も系列ごとに同じ優先順・同じ閾値で独立に出す。
  本番列の gpu_gap は層出力のゼロ初期化を含まず、host の発行待ちによる GPU の空きだけになる（#3189 列は確保＋ゼロ初期化 2 回分を含む）。
  E_sum = l1_iso + l2_iso（実測。起動立ち上がりを含む融合カーネルの GPU 実行幅。出力のゼロ初期化を含まない）。chain_gpu（実測。層出力のゼロ初期化を含む）。
  gpu_gap = chain_gpu − E_sum（実測の差。負値もありうる。層出力のゼロ初期化 2 回分・host の確保／発行待ちによる GPU の空きを含む）。
  host_issue_sum = P の l1_issue + l2_issue。gpu_tail = max(0, chain_gpu − host_issue_sum)（推定）。
  wait_resid = kernel_wait_derived − gpu_tail（推定。起動遅延・同期復帰・event tracking 等。tiny_roundtrip と並べて読む）。
  share_exec = E_sum / kernel_wait_derived（推定。融合カーネル本体の割合で、ゼロ初期化は share_wait 側に入る）。share_wait = 1 − share_exec。
  event_perturbation = E 腕 download / P 腕 download − 1（実測）。
  分類（優先順に固定し事後に動かさない）:
    1. event_perturbation > 0.10 なら確度を必ず「低」にし理由を書く。
    2. share_exec ≥ 0.5 なら「GPU 実行が支配」（GPU 実行は融合カーネル本体を指し、層出力のゼロ初期化を含まない）。
    3. それ以外は「待ち（起動遅延・間隙・同期復帰）が支配」。
    4. 確度「高」は、全 round が 0.5 の同じ側かつ NB-RANGE5 帯が 0.5 をまたがない場合のみ。それ以外は「低」。
  副次: l1_iso・l2_iso を docs/perf/infer-chain-fixed-cost-reduction-3205.md §3 の「占有率」推定と突き合わせ、推定のまま残すか実測で置き換えるかを結果欄に書く。
  相手側（#4149 実測）が入手できる場合のみ aggregate_4150.py --opp-tsv で対応表を出す。無ければ unavailable（推定で埋めない）。
  対応は本番列と取る（#4149 の X は device 上で H2D を含まず、本番列も H2D を含まない）。#3189 列は参考として並べる。
  非対称（本番列）: fandhe の l1_iso／l2_iso は bias＋ReLU 融合込みの同じカーネル（into 経路）、PyTorch の mm_event は純 GEMM。fandhe の窓は facade 上位の固定費を含まない。
  非対称（#3189 列のみ）: fandhe の窓は H2D を含み PyTorch 側は X が device 上で H2D を含まない。
    fandhe の chain_gpu は層出力のゼロ初期化を含む（PyTorch の caching allocator は層ごとのゼロ初期化をしない）。
