  セクション・`.cargo/config.toml` はコミットしていない（CLI `--config` 引数のみ）。
  ビルド後は `GEMM_GATE_SKIP_BUILD=1` で測定 run を実行し、以後 `cargo build`/`cargo tree` を
  一切呼ばずに測定を完了させた（plain `cargo build`/`cargo tree` を測定 run の前後に挟むと
  Cargo.lock の解決が registry 側へ暗黙に巻き戻り、意図しない登録版バイナリへ差し替わる事故を
  実際に踏んだため。§「参考系列ビルドの事故と対処」参照）
- `bench-candle` は両系列で共通の 1 バイナリ（`fandhe-ai` に依存しないため）

## 参考系列ビルドの事故と対処（記録）

1 回目の参考系列ビルド直後、確認のため引数なしで `cargo tree -p bench-fandhe --depth 1` を
実行したところ、Cargo.lock が registry 解決へ暗黙に再ロックされた（`--config patch` は単発
invocation にのみ適用され、Cargo.lock 自体には path 解決が永続化されないため）。その状態を
知らずに `GEMM_GATE_SKIP_BUILD` なしで測定 run を起動してしまい、`run_gemm_gate_cuda.sh` の
「build bench-fandhe」ステップが（`--config` なしのため）registry 版 binary
（`target/release/deps/bench_fandhe-92fe7ffa143d50cf`。Phase B 正式系列ビルドと同一 hash
のため即座に再リンクされ、見た目上ビルドが一瞬で終わった）へ差し替えて計測を開始した。
10 レコード（N=1024/2048・run 1〜2）が誤って登録版 binary で記録された時点で気づき、
プロセスを kill・該当 JSONL/ログを削除し、`--config patch` を再指定してビルドし直した上で
（`target/release/deps/bench_fandhe-fe9083cb0b6ff30a`。size/mtime を hardlink 一致で確認）、
以後は `cargo build`/`cargo tree` を挟まず `GEMM_GATE_SKIP_BUILD=1` で測定した。誤登録された
10 レコードは正式な参考系列データとして使用していない（記録のみ・数値は本ファイルに残さない）。
