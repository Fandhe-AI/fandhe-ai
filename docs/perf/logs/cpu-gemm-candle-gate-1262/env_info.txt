## 実行 1 回目（並走ゲートにより破棄）
- 開始直後の `pgrep` 確認で、他セッションの CPU ゲート（label `head-145639d-pzero-on`）・
  CUDA ゲート（label `1437after-off`、後に `1437after-on` の CUDA ビルド `cicc`/`rustc`
  100〜423% CPU）が同一ノードで並走していたことを事後に確認した（隔離ディレクトリの
  rsync 完了直後に実行を開始したため、並走確認と起動が競合した）
- `uptime`: 起動時 load average 5.23 → 完了時 17.17/10.32/5.05（自 run 分のみでは
  説明できない上昇）。**破棄の根拠は比の乖離ではなく、この期間中 `pgrep` で実際に競合
  プロセス（他セッションの CPU/CUDA GEMM ゲート・cargo ビルド）が動作していたことを
  直接確認した点にある**（測定と競合プロセスの起動が時間的に重なっており、CPU 論理
  コアを奪い合う実負荷混入は構造的に避けられない状態だった）。参考までに 1 回目の
  candle/fandhe 比は N=512 0.745・N=1024 0.793・N=2048 0.938（結果ファイルは
  `results/raw/*1262*.discarded-contended` として隔離ディレクトリ側にのみ残し、
  回収していない。commit 対象外）で、2 回目（0.862／0.778／0.950）とは方向感が一致
  しない項目（N=1024 は 1 回目の方が §12.2 の 0.786 に近い）もあり、比の大小のみからは
  どちらが「正しい」かを機械的に判定できない。したがって**採否は比較ではなく競合
  プロセスの有無という直接的な事実に基づく**
- **parity 判定自体（N=2048 の `fail=0, rescued=2, bound=1.525878e-05`）は 1 回目でも
  2 回目と完全に同一の決定的な値であり、負荷の影響を受けていない**（bit 決定的な
  candle-core カーネル挙動のため。§19.3 参照）

## N=2048 比の妥当性根拠（2 回目採用値 0.950 倍）

- イシュー #1185（§12.2）の DGX 側生データ（`results/raw/results-dgx-cpu-gemm-gate-
  0.7.0.jsonl`。当時 N=2048 は candle 側 parity fail のため「判定不能」として比を
  確定表示していなかった）から N=2048 の median（fandhe-ai reuse・candle fresh）を
  算出すると candle/fandhe ≈ 0.968 倍（fandhe reuse median 0.034877 s・candle fresh
  median 0.033750 s）であり、本追補の採用値 0.950 倍と近い水準にある。tolerance 契約
  変更は判定方式（fail-closed の可否）のみを変えるものであり性能値自体には影響しない
  ため、この近さは 2 回目の計測が異常値ではないことの参考傍証になる

## 計測前後のアイドル確認（採用した 2 回目の run）
- 1 回目完了直後、`pgrep -af "run_gemm_gate.sh|cargo build|rustc|cicc"` で他セッションの
  競合プロセスが検出されなくなるまで 30 秒間隔でポーリングし、`uptime` の 1 分平均
  load average が 4.0 未満（`docs/perf/cpu-gemm-candle-gate-remeasurement.md` §17.2 の
  専有ゲート閾値と同一基準）になった時点で即座に競合プロセス再確認後に起動した
  （チェックと起動の間隙を最小化する atomic launch。ビルド成果物は 1 回目でキャッシュ
  済みのため 2 回目はビルドなしで即計測に入った）
- 起動直前: `pgrep -af "run_gemm_gate.sh|cargo build"` 該当なし・load average 3.56
  （直前ポーリング時点）
- `run_gemm_gate_cpu.sh` 内部の `cpu status (before)`: load average 3.28/7.01/5.00
  （20 コア中の使用率としては低〜中程度。5 分・15 分平均にはまだ 1 回目実行の残余が
  含まれる）
- 計測完了直後: `cpu status (after)` load average 5.60/7.10/5.13（自 run による上昇を
  含む。計測中に他セッションの `run_gemm_gate.sh`／`cargo build`／`rustc`／`cicc` が
  再出現していないことを計測中の複数回の `pgrep` 確認で確認済み）
- **完全な専有（load average が実測前の基準値近傍まで下がる状態）は最後まで確保できな
  かった**が、計測中に本ベンチと直接競合する他プロセス（CPU/CUDA GEMM ゲート・cargo
  ビルド）が存在しないことを `pgrep` で確認しており、N=512/1024 の実測値（0.862／0.778
  倍）が §12.2 の正式系列値（0.810／0.786 倍）と誤差範囲内で一致することからも、
  1 回目のような重度の負荷混入は解消されていると判断した
