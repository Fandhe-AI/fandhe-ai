- OS: macOS（Darwin 25.6.0）
- rustc/cargo: stable（`rustc --version` は `bit-exact-large-m4max.txt` 参照）
- RAYON_NUM_THREADS: 未設定（既定で全 16 論理コア使用）
- 計測日: 2026-09-07（UTC）
- worktree HEAD: `0e9110f`（`origin/main` 追従。`IcDynamic` を含む）
- 負荷状態: 本マシン上で並列稼働する他の Claude Code エージェントセッションが多数
  存在し、計測中の `uptime` load average は 22.18〜31.11（16 論理コアに対し極めて
  高い共有負荷）で推移した（`uptime-m4max.log`）。計測を専有できる低負荷窓が
  取れなかったため、計画（plan §Step 1-1）に従い「共有負荷下」として実行した。
  M4 Max の値は DGX と比較しノイズが大きい点に留意する（N=2048 の RowPanel は
  609〜786 GFLOP/s の範囲で run 間ばらつきが大きい）
- bit 完全一致: `bit-exact-large-m4max.txt` に pass ログを含む
- 生ログ: `ab-1024-2048-m4max-run{1..5}.txt`・`ab-4096-m4max-run{1..5}.txt`
- OSS 直接比較参考値: `oss-m4max-run1.txt`（1 回のみ・`self_gemm_blis_parallel` は
  本番 `RowPanel` 経路。`oss-gemm-compare` ハーネスは variant 選択に非対応のため
  `IcDynamic` 単体の対 gemm crate 比は計測不能。matrixmultiply 側の
  `output_match=false` は既知の丸め差〈rel_diff 〜0.005〉で fail-closed 仕様どおりの
  想定内挙動）

## 集計

`aggregate.py`（python3 標準ライブラリのみ）で両実機の生ログから中央値・比を再計算
できる。実行例:

```
python3 aggregate.py "DGX Spark GB10" ab-1024-2048-dgx-run1.txt ab-1024-2048-dgx-run2.txt \
  ab-1024-2048-dgx-run3.txt ab-1024-2048-dgx-run4.txt ab-1024-2048-dgx-run5.txt \
  ab-4096-dgx-run1.txt ab-4096-dgx-run2.txt ab-4096-dgx-run3.txt ab-4096-dgx-run4.txt ab-4096-dgx-run5.txt
```

結果は `docs/perf/cpu-gemm-candle-gate-remeasurement.md` §14.4／§14.5 の表と一致する。
