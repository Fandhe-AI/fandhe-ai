- OS: Darwin（arm64）

- BIG_CORE_LIMIT_ENABLED: false（#1364 確定のまま不変）
- 転送方式: ローカル worktree で直接実行（rsync 不要）
- 負荷状態: 共有負荷下（他セッションの並列実装ジョブと同居する M4 Max。実測開始前
  `uptime` は load averages 1.14/1.63/2.56。1024/2048 系列実行中に load averages が
  一時的に 5〜6.4 台まで上昇（`uptime-m4max.log` 参照）。共有負荷下である旨は
  ノイズガード判定・結論の解釈に反映する
- **`uptime-m4max.log` の既知の欠落**: DGX へのコード転送（rsync）が
  `run_m4_ab.sh`（M4 Max の 1024/2048/4096 系列を順次実行するバックグラウンド
  スクリプト）の実行途中に行われ、その時点の `docs/perf/logs/` スナップショットが
  DGX 側にも同期された。DGX 側の A/B ログ回収（`scp` でディレクトリ全体を
  ワイルドカード取得）の際にこの中間スナップショットが逆流し、ローカルで
  進行中だった `uptime-m4max.log`（本来は計測開始前 1 回＋各 run 後 10 回の
  計 11 行）を「1024 系列前半までの 6 行」で上書きした。その後 4096 系列
  run1（`ab-4096-m4max-run1.txt`）のみ、出力が空だったため独立プロセスとして
  再実行し（再実行時刻・負荷は本ファイル末尾の 7 行目 `7:39 … load averages:
  6.07 5.04 4.01` に対応）、その 1 行のみが追記された。結果として
  `uptime-m4max.log` は 1024/2048 系列後半・4096 系列 run2〜5 の負荷サンプルを
  欠く（7 行のみ）。各 A/B ハーネス出力ファイル（`ab-*-m4max-run*.txt`）自体は
  この上書きの影響を受けていない（1024/2048 の 5 run は上書き前のスナップショット
  時点で既に完了・記録済みで、4096 run1 は上書き後に独立して再実行し直したため）。
  この欠落は M4 Max の負荷状態サンプルの一部が失われたことのみを意味し、
  §8.2 の REJECT 判定は低負荷ゲート成立済み・uptime ログが完全な DGX Spark GB10
  側の結果（N=1024/2048 とも 1.00 未達）で成立しており、M4 Max はこれを補強する
  位置づけとして扱う
