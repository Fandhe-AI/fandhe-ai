# Mac mini の Metal GEMM タイル選択の追跡と全候補の純カーネル時間（イシュー #3181）

**診断のみ**。選択ロジック（`tile.rs`）・`gemm.rs`・`shaders/`・tolerance・split-K parity baseline・相手側ベンチのコードは変えていない。
規則の正は `docs/perf/logs/metal-tile-macmini-3181/RULE.txt`（計測前に固定）。生ログと機械集計は同ディレクトリ
（`aggregate.md` が全表）。判定ゲートはなく、分類は RULE 項 14 の記述ルールによる。

## 0. 結論

1. **AC1（実際に選ばれたタイル）**: Mac mini（Apple M4・GPU 10 コア）では `verified_m4_max=false`。N=256 / 512 / 1024 / 2048 / 4096 のすべてで
   `should_split_k=none`・経路は `Classic`・要求も解決（fallback なし）も `CANDIDATES[3]`（32×32×16・wm2×wn2・staged）だった。5 run で全一致。
2. **AC3（`CANDIDATES[3]` 選択の推測）: 実測で支持された**（全 5 サイズ）。split-K に入らないという推測も、同じ trace で支持された。
3. **AC2（全候補の純カーネル時間と candle 比）**: 表は §3・§4。要点は次のとおり。
   - `CANDIDATES[3]` は N=512 以上で最良ではない。fallback のない 11 候補のうち kernel_gpu 最小は N=512 / 1024 が `[1]`（64×32×16）、N=2048 / 4096 が `[2]`（32×64×16）。
     選択比（最良 / 選択）は 0.946 / 0.934 / 0.812 / 0.821。5 run すべてで最良が選択より速い。
   - その差を全部取り戻しても candle には届かない。N=4096 は最良 `[2]` でも candle excl の 0.795（kernel_gpu 比。candle に有利な偏りなし側の参考比）。
   - N=256 は kernel_gpu が 0.020 ms で、壁時計合計 0.256 ms の約 8%。タイルではなく固定費（出力確保・encode・commit/wait）が支配的。
4. **RULE 項 14(b) の分類**: N=512 / 1024 / 2048 / 4096 は「**Mini 専用表の候補あり（#3206 へ）**」、N=256 は「現行選択と帯内（専用表は不要）」。
   M4 Max 実測表と順位が一致するのは N=4096（どちらも `[2]`）だけで、512 / 1024 / 2048 は一致しない（§5）。専用表の追加は #3206 のスコープで、本イシューでは行わない。
5. **後続 3 件への示唆**（因果の断定ではなく、観測から言えること）:
   - #3206（Mini 専用表）: 2048 / 4096 でカーネル時間を約 18〜19% 縮められる余地を実測で確認。512 / 1024 は 5〜7%。
   - #3208（m=64）: 本イシューは正方形状のみ。m=64 は未測定で、ここからは何も言えない。
   - #3211（candle 構造の再現）: 表の取り直しで最良候補になっても N=2048 / 4096 は candle の 0.83 / 0.80 倍にとどまる。タイル選択だけでは埋まらない差が残る。

## 2. 選択の追跡（AC1・AC3）

5 サイズとも同一の行になる（`aggregate.md` (i)）。

| N | `select(N,N,N)` | `select_for_device(…, None)` | `should_split_k` | 実行経路 | 解決構成 | AC3 |
|---|---|---|---|---|---|---|
| 256 / 512 / 1024 / 2048 / 4096 | `[3]` 32×32×16 | `[3]` | none | `Classic/[3]` | `[3]`（fallback なし） | 支持 |

`select_for_device` に渡す `verified` が `None`（Mini は 40 コア・M4 Max ブランドの照合に通らない）なので、M4 Max の厳密一致表は使われず、
`m==n==k<=4096` の既定である `CANDIDATES[3]` が返る。

## 4. candle との比

速度比 = candle 時間 / fandhe 時間。1 未満は fandhe が遅い（イシューの reuse 比と同じ向き）。

| N | candle excl ms | 主比（excl ÷ fandhe 壁時計合計、選択 `[3]`） | 参考比（excl ÷ fandhe kernel_gpu、選択 `[3]`） | 参考比（最良候補の kernel_gpu、idx） |
|---|---|---|---|---|
| 256 | 0.2170 | 0.848 | 10.741 | 10.741 (3) |
| 512 | 0.3225 | 0.832 | 2.763 | 2.921 (1) |
| 1024 | 0.9254 | 0.689 | 1.059 | 1.133 (1) |
| 2048 | 5.4482 | 0.608 | 0.676 | 0.832 (2) |
| 4096 | 42.3923 | 0.626 | 0.652 | 0.795 (2) |

注（境界の違い）:

- candle excl は A・B をループ外で 1 回だけ転送し、計測窓は `matmul + Device::synchronize()` のホスト壁時計。出力確保と encode と同期を含む。
  fandhe の kernel_gpu は GPU タイムスタンプで、これらを含まない。**どちらの比も「純カーネル比そのもの」ではない**。
- 主比は壁時計どうし（fandhe の `alloc_c + encode + commit_wait`）で、境界が最も近い組み合わせ。
- 参考比は candle 側に encode と同期のぶんが余計に入るため、fandhe に有利に偏る。小さい N で値が大きいのはそのため。
- N≥2048 は固定費が相対的に小さく、主比と参考比の差が縮む（2048: 0.608 と 0.676）。この領域では参考比が純カーネル比に近づくと推測されるが、境界が揃っていないので断定しない。
- 主比（選択 `[3]`）の N=4096 は 0.626。最良候補 `[2]` の壁時計合計（56.09 ms）で置き換えると 0.756、N=2048 は 0.730（いずれも `aggregate.md` の値からの算出）。

## 5. M4 Max の既存表との比較

M4 Max の厳密一致表（`docs/perf/metal-gemm-tile-table.md`・`docs/perf/metal-gemm-n4096-kernel-gap.md` §0）が選ぶタイルと、Mini の最良は次のとおり。

| N | M4 Max の選択 | Mini の最良（本実測） | Mini の選択（現行） |
|---|---|---|---|
| 256 | `[3]` | `[3]` | `[3]` |
| 512 | `[5]` | `[1]` | `[3]` |
| 1024 | `[6]` | `[1]` | `[3]` |
| 2048 | `[1]` | `[2]` | `[3]` |
| 4096 | `[2]` | `[2]` | `[3]` |

- N=4096 だけは Mini でも `[2]` が最良で、M4 Max と一致した。N=512 / 1024 / 2048 は順位が違う。GPU コア数（10 と 40）の差と見るのは自然だが、
  本実測は Mini 1 機のみで原因までは確かめていない。
- Mini で `[5]`（512 の M4 Max 選択）は選択 `[3]` と同等（0.1187 対 0.1167 ms）、`[6]`（1024）も同等（0.8726 対 0.8738 ms）で、M4 Max の表を Mini にそのまま流用しても 512 / 1024 では最良 `[1]` に届かない。

## 7. 限界

- 機体は Mac mini 1 台・共有機（計測中の他プロセスは確認していないが、load1 は全プロセスで 3.0 未満）。
- 正方 NN のみ。転置・非正方・m=64 は対象外。
- candle の計測コードは変えていない（壁時計のみ。GPU タイムスタンプは取れない）。
- 計測前コミット（`bc5b42bcf…`）の後に追加したのは成果物と doc だけで、計測対象のコードと規則は変わっていない。
  なお `aggregate.py` は計測後に 1 点だけ直した（candle の JSONL がフラットなスキーマ `median_s`／`version` だったため、パース箇所を合わせた）。値・判定には影響しない。
- 生ログのパスは `<WORK>`／`<HOME>` にマスクしてある。
