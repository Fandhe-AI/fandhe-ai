# m=64 級 GEMM の job 分割・再 pack・確保の回数診断（イシュー #3177）

MLP（784→256→10・batch 64）の CPU 学習・推論で、小形状 GEMM の固定費として疑われる
4 項目（(mc, nc) 2D 動的分配の job 細分化・A の job ごと再 pack・job ごとの `vec!` 確保・
C の job-local コピーイン／アウト）を、実行ログで数えるための診断基盤と結果を記録する。
**診断のみ**で、本番の既定値とコードパスは変えていない。事前登録規則は
`docs/perf/logs/cpu-jobgrid-3177/RULE.txt`。

## 2. job 数・再 pack の計数（Mac mini・GB10 実測。正式系列）

NEON MR=8／NR=12、`jpw=2`。腕は native（機体の既定プール。Mac mini 10・GB10 20 スレッド）と専用 `ThreadPool` の T=1／10／20。
5 run で `regions`・`jobs`・pack 語数・確保回数が全一致（`workers_used` は Rayon のスケジューリングで run 間に変わるため記録のみ）。
表は T10／T20 の一部で、全腕・全形状・`workers_used` は `docs/perf/logs/cpu-jobgrid-3177/aggregate.md` を正とする。

| 形状 | T=10 job（行帯×列帯） | T=20 job | A 再 pack 倍率（T=10／T=20） | B 再 pack 倍率（T=10／T=20） |
|---|---|---|---|---|
| L1 fwd 64×256×784 Nn | 22（2×11） | 44（4×11） | 11.0／11.0 | 2.0／4.0 |
| L1 dW 784×256×64 Tn | 20（10×2） | 40（10×4） | 2.0／4.0 | 10.0／10.0 |
| L1 dX 64×784×256 Nt | 22（1×22） | 44（2×22） | 22.0／22.0 | 1.0／2.0 |
| L2 fwd 64×10×256 Nn | 8（8×1） | 8 | 1.0／1.0 | 8.0／8.0 |
| L2 dW 256×10×64 Tn | 32（32×1） | 32 | 1.0／1.0 | 32.0／32.0 |
| L2 dX 64×256×10 Nt | 22（2×11） | 44（4×11） | 11.0／11.0 | 2.0／4.0 |

- **再計算との突合**: Mac mini・GB10 とも、native・T10・T20 の 3 腕 × 6 形状 = 18 件（機体ごと）すべてで job 数・行帯×列帯・A／B 再 pack 倍率が
  再計算（Issue の 22／44 job・A を 11 回再 pack ほか）と**一致**した（不一致 0 件）。native は Mac mini が T10、GB10 が T20 と同じ値になる。
- 確保回数は job 内 3 回 × job 数（L1 fwd は T10 で 66、T20 で 132）と `split_c_into_jobs` 側 37／59 回。rayon 内部の確保は含まない解析値。
  C staging は 1 GEMM あたり L1 fwd 32768 語・L1 dW 401408 語・L1 dX 100352 語・L2 fwd 1280 語・L2 dW 5120 語・L2 dX 32768 語（`2×m×n`）。
- T=1 では全形状で job 1 個・確保 3＋6 回。再 pack 倍率は 1.0（L1 dX の A のみ 2.0。原因は未調査で、本 issue の対象外）。
- L1 dX（64×784×256 Nt）は入力が勾配を要求しない学習では本番で実行されない可能性がある。未確認のため、本番での実行有無は結論に使わない。

- 規則どおり 5 プロセスの中央値を採った。ただし **run 間のばらつきが大きい形状がある**。GB10 の L1 fwd は 36／105 の 2 つの水準に割れ（5 run 中 3 run が 36）、
  中央値は低い側になる。Mac mini は run1 だけ全形状で低い（40.2／62.5／72.4 ほか）。原因は未検証である。
  GB10 は性能の異なる 2 種のコア（Cortex-X925 と Cortex-A725 が各 10 個。`env_info.txt`）を持ち、単スレッドのプロセスが載るコアで水準が割れた可能性があるが、
  コア親和性は記録していないため推定にとどまる。中央値を 1 つの代表値として使う際は、この 2 水準を併記すること。
- 単スレッドの実効値は L1 dW／L1 dX で約 92〜100 GFLOPS（正方 512 の 75〜85%）、L2 の細い形状（n=10 や k=10）で約 29〜44 GFLOPS（同 25〜36%）。
  fwd の L2（64×10×256）と dW の L2 は n=10 が NR=12 に満たず、タイルの無駄が出る形である（本 issue では原因を確かめていない）。
- 前回の開発機（M4 Max）の動作確認値は非正式のため、本表には載せない。

## 4. job 分割 A/B（`jpw1`／`cap4`／`cap8` 対 base。採否は決めない）

腕は base（main のまま `TWO_D_JOBS_PER_WORKER=2`）・`jpw1`（`=1`）・`cap4`／`cap8`（`job_grid_with_trace` の `bound` に `.min(4)`／`.min(8)` を追加）。
差分は `logs/cpu-jobgrid-3177/ab_patch_*.diff`（各 1 ファイル 1 行）で、計測用の複製ツリーにだけ当てた。main には当てていない。
既定プール（Mac mini 10・GB10 20 スレッド）、5 run、腕の起動順は run ごとにローテーション。全 42 セル（機体 2 × 形状 7 × 腕 3）で checksum は全腕・全 run 一致。
ratio = median(腕)／median(base)（1 未満が腕の勝ち）、括弧内は 5 run 中に腕が base に勝った run 数。

読み取れる事実（採否ではなく #3198／#3227 への入力）:

- GB10（20 スレッド）では `jpw1` が L1 の 3 形状と L2 dX で 0.82〜0.94 と一貫して速い（L1 fwd・L1 dX・L2 dX は 5 run 全勝）。
  `cap4`／`cap8` は 20 スレッドのうち 4〜8 しか使わないため、GB10 では全形状で base より遅い（L1 fwd cap4 が 2.5 倍）。
  正方 512 は `jpw1` でも 1.42 倍遅くなり、細長い形状と大きい形状で最適が逆になる。
- Mac mini（10 スレッド）では差が小さい。`cap4` は L1 dW・L1 dX で 0.83〜0.85（4 run 勝ち）、`jpw1` はほぼ中立（L2 の細い形状で 1.06〜1.14 の悪化もある）。
  ばらつきは 1 run あたり数 % あり、勝ち run 数が 2〜3 の cell は優劣を断定できない。
- 数 μs〜100 μs の形状のため、スレッドスケジューリングの揺らぎ（§3 の run 間の水準差と同じ性質のもの）を含む。
  既定値の変更（#3227）は、この表と §2 の再 pack 倍率を入力に、形状別の閾値設計（#3198）と合わせて判断する。

## 5. 未実施・限界

- 実機の計測は Mac mini・GB10 とも `docs/perf/logs/cpu-jobgrid-3177/` に収録した 1 系列のみ（再実行・差し替えなし）。負荷ゲートは全 35 プロセスが通過したが、
  Mac mini はビルド直後の自身の負荷が load1 に残っており（最初のゲート通過時 4.5。閾値 5.0 未満。180 秒待って通過。全 35 プロセスが約 5 秒で完走したため、計測全体がこの負荷下にある）、GB10 は他の利用者の load1 約 3.6 が常在する共有ノードである。
- 単スレッドの run 間ばらつき（§3）の原因（コア種・ターボ・起動直後の周波数）は未検証。
- L1 dX が本番の学習で実行されるか、T=1 で L1 dX の A pack 倍率が 2.0 になる原因は調べていない（スコープ外）。
- job 分割・pack 共有・確保削減の実装は #3198、既定値の変更は #3227。本 issue では本番の既定値とコードパスを変えていない。
