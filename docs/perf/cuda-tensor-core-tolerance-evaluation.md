### NVRTC プロビジョニング（本リポジトリの CUDA toolkit 非搭載環境での実測手順）

本実行環境には `libcuda`（driver）はあるが `libnvrtc`（NVRTC 実行時コンパイラ）を含む CUDA toolkit が
未導入だったため、以下の手順でプロセス限定のプロビジョニングを行った（システムへの `apt install`・
`/usr/local` への配置は行わない。グローバル状態を汚さない best-effort 手順）。

```bash
pip install --target <SCRATCH>/pylibs --no-deps \
  "nvidia-cuda-nvrtc==13.2.86" "nvidia-cuda-runtime==13.2.86"
# WMMA カーネルが #include する <mma.h> は "crt/mma.h" を再 include するが、
# pip 配布の nvidia-cuda-* wheel には crt/ サブディレクトリが含まれていない
# （ランタイム限定パッケージのため）。apt-get download で crt/mma.h のみを
# 取得し、pip wheel の include/ 配下に重ね合わせる（apt install はしない。
# パッケージを .deb のまま展開するのみでシステムへは導入しない）。
apt-get download cuda-crt-13-1
dpkg -x cuda-crt-13-1_*.deb <SCRATCH>/deb-extract
cp -r <SCRATCH>/deb-extract/usr/local/cuda-13.1/targets/x86_64-linux/include/crt \
  <SCRATCH>/pylibs/nvidia/cu13/include/

# 重要（#186・PR #257 Codex Review 指摘対応）: LD_LIBRARY_PATH・
# CUDA_INCLUDE_PATH は cargo build 時「だけ」でなく実行時（バイナリ起動時）
# にも必要である。NVRTC は CudaGemm::new / CudaWmmaGemm::new 呼び出し時
# （＝バイナリ実行中）にカーネルソースを実行時コンパイルするため、
# ビルド後にこれらの環境変数が失われた状態で実行すると
# 「NVRTC 非搭載環境のためスキップします」という誤った skip 判定になる
# （NVRTC 自体は使えるのに、動的ロードが失敗したように見えてしまう）。
# ビルドと実行を同一シェルセッション内で行うか、下記のように 1 コマンドで
# 環境変数を明示して両方に渡すこと。
export LD_LIBRARY_PATH=<SCRATCH>/pylibs/nvidia/cu13/lib:$LD_LIBRARY_PATH
export CUDA_INCLUDE_PATH=<SCRATCH>/pylibs/nvidia/cu13/include

cargo build --release -p backend-cuda --example wmma_tolerance_probe
./target/release/examples/wmma_tolerance_probe   # ビルドと同じ env が有効なシェルで実行する
```

**バージョン選定の注記**: driver 595.71.05 は `CUDA Version: 13.2` までの PTX を受理する
（`nvidia-smi` 表示）。当初 `nvidia-cuda-nvrtc==13.3.33`（pypi 最新）で試したところ
`CUDA_ERROR_UNSUPPORTED_PTX_VERSION` で失敗したため、driver の対応範囲内である `13.2.86` に
ダウングレードして解決した。`crt/mma.h` は CUDA 13.1 の `cuda-crt` パッケージから取得したが、
`mma.h` の内容は minor version 間でも安定しており、compute_86 向け WMMA コンパイルに問題は
生じなかった（本ドキュメントの全実測がこの構成で成功していることが根拠）。

この手順は #64（TASK-11.1e・GB10 実機）でも再利用可能な NVRTC プロビジョニング手順として記録する。

## 2. 誤差分布実測表

各形状につき 5 シードを計測し、シード間の `fail_count` 合計・`max_abs_diff`／`max_rel_err`／
`max_fail_abs_diff` の最大値を集計した（統計手法は `docs/perf/cpu-gemm-rayon-tuning.md` の記録形式に
倣う）。シードごとの生データ（`CompareReport` 全項目。`max_fail_abs_diff` を含む）は本ドキュメントに
転記した計測コマンドを再実行すれば決定的に再現される（プローブの `report_row` は `CompareReport`
の全フィールドを出力する。#186・PR #257 Codex Review 指摘対応）。**ただし TF32 側（§2.1）は
上記「測定条件の失効に関する注記」のとおり、`wmma_tf32_opt`（TASK-11.1d／#63）が利用可能な環境で
再実行すると異なるカーネルを計測することになり、同一内容の再現は保証されない**（f16 側／§2.2 は
本改訂の変更対象外のため影響を受けない）。

閾値（変更対象外）: `RELATIVE_TOLERANCE = 1e-3`、`ABSOLUTE_RESCUE_THRESHOLD = 1e-5`。

`max_fail_abs_diff` は fail したセル（複合判定で不合格）に限定した `abs_diff` の最大値であり、
「fail セルを救済しうる絶対誤差救済閾値の infimum（下限）」を意味する（**この値そのものを閾値に
設定しても救済されない**点に注意: `compare` の判定式は `diff < ABSOLUTE_RESCUE_THRESHOLD`（狭義不等号）
であり、`ABSOLUTE_RESCUE_THRESHOLD == max_fail_abs_diff` では当の最大値を持つセル自身が
`diff < threshold` を満たさず未救済のまま残る。加えて本表の値は表示のため `{:.3e}` で丸めた値であり、
実際の閾値候補は丸め前の最大値を厳密に超える必要がある。#186・PR #257 Codex Review 再指摘対応）。
`max_abs_diff`（全セル対象）は PASS セル由来の場合があり、絶対誤差救済閾値の改定根拠には
使えない（#186・PR #257 Codex Review 指摘「複合判定（相対誤差・絶対誤差）の max 値がそれぞれ別要素
由来の可能性があり、絶対誤差救済閾値 1e-2 案の根拠として max_abs_diff は不十分」対応。§3 で両者の
差を実測データで示す）。

> **注記（意図的な重複マージ）**: ハーネスの `SHAPES` 定数は 16 形状だが、「256×256×256
> (block tile x8)」と「256×256×256 (K sweep base)」は m=n=k=256 で完全に同一の形状であり
> シード導出式（`m` 由来）により同一入力・同一結果になる（
> `crates/backend-cuda/examples/wmma_tolerance_probe.rs` の `SHAPES` コメント参照）。
> そのため下記 §2.1・§2.2 の実測表はいずれも 15 行とし、重複分は「256×256×256（block tile ×8）」
> の 1 行にマージして記録している（計測が 1 件欠落しているわけではない）。
>
> **1×1×1 の縮退**: 「1×1×1（sub-K-tile）」形状は要素数 1（`total=1`）のため、5 シードとも
> `max_abs_diff == p50_abs_diff == p99_abs_diff == p999_abs_diff` に縮退する（分布統計としての意味を
> 持たない、単一値の記録）。`margin()` は誤差が 0 の場合 `inf` を返す実装のため、他形状で誤差 0 の
> セルがあった場合も同様に `inf` と表示される（不具合ではない）。

## 3. 閾値評価

### 3.1 TF32 丸め誤差の理論値（訂正）

旧版（初回実測時点の記述）は TF32 の理論誤差下限として「仮数部 23bit を 10bit に丸めるため
2^-10 ≈ 9.8e-4」とだけ述べていたが、これは spacing（丸め幅）と unit roundoff（丸め操作 1 回の
最大相対誤差）を混同しており、GEMM 全体の誤差との関係も不明瞭だった（#186・PR #257 Codex Review
指摘「TF32 の理論下限として 2^-10（spacing）を使っているが、round-to-nearest の最大単発丸め誤差は
2^-11 程度であり、閾値 1e-3 の妥当性根拠として数値的に誤解を招く」対応）。以下の 3 つの量を区別する:

- **spacing（ulp）@ 1.0**: TF32 は仮数部が明示的に 10bit（正規化数の暗黙 1 bit を含め有効 11bit
  ≈ FP32 の 23bit からの丸め）であり、1.0 近傍の値の刻み幅は 2^-10 ≈ 9.77e-4。
- **unit roundoff（u）**: round-to-nearest 1 回の丸めが生む最大相対誤差は spacing の半分、
  すなわち u = 2^-11 ≈ 4.88e-4。
- **dot-product（GEMM 1 要素）の誤差**: TF32 パスは入力 A・B をそれぞれ TF32 に丸めてから積和する
  （`crates/backend-cuda/src/kernels.rs` の `wmma::fragment<matrix_a/matrix_b, ..., precision::tf32, ...>`）
  一方、累算は `wmma::fragment<wmma::accumulator, ..., float>`（FP32）で行われる。したがって GEMM
  1 要素の誤差は主に**入力側の丸め**（各項 a_k・b_k がそれぞれ最大相対誤差 u で丸められる）に支配され、
  近似的に `2u × (Σ|a_k b_k| / |Σ a_k b_k|)`（条件数）程度になる。

**FP32 累算誤差項の扱い（訂正。#186・PR #257 Codex Review 再指摘対応）**: 旧記述は「FP32 累算自体が
追加する誤差は K・2^-24 のオーダーで無視できる」としていたが、この判断は数値的に不十分である。
K=4096 では `K·2^-24 ≈ 4096 × 5.96e-8 ≈ 2.44e-4` であり、これは現行 `RELATIVE_TOLERANCE`（1e-3）の
約 1/4、かつ上記 TF32 入力丸め項 `2u ≈ 9.77e-4` の約 1/4 に相当する大きさで、「無視できる」と言い切れる
差ではない。さらに、桁落ちキャンセレーション（真値がゼロ近傍に相殺される場合に相対誤差が増幅される
§3.1 後段の議論）は入力丸め誤差だけでなく累算誤差にも同様に作用しうるため、累算誤差項を分離せずに
「fail 率の K 非依存性は入力丸めが支配項であることの証拠」と断定することはできない。

**本イシューでは累算誤差項の定量的な切り分けを実施していない**（未実施の検証として記録する）。
切り分けには、TF32 丸め済みオペランド（`a_k`・`b_k` をあらかじめ TF32 精度相当に丸めた値）を用いて
FP32 累算のみで積和する参照実装を別途用意し、本ハーネスの実測値との差分から純粋な累算誤差寄与を
分離する実測が必要である。この定量化が完了するまで、「fail 率が K に依存しないのは入力丸め×条件数が
支配項であるため」という帰属は**仮説として記載するにとどめ**、閾値改定の定量的根拠（§3.2・§4）には
累算誤差項を無視した前提を用いない。

実測（§2.1）の「fail 率が K=256〜4096 でほぼ横ばい（15.8%〜16.5%）」という観察自体は変わらないが、
上記のとおり累算誤差項を定量化していない以上、この観察から「入力丸め×条件数が支配項である」と
結論づけることは**未検証の仮説**の域を出ない。

実測される `max_rel_err` は最大 1.98（198%）に達しており、これは仮数部丸め単独（u ≈ 4.9e-4）では
説明できない大きさだが、GEMM の出力要素が真値としてゼロ近傍（K 項の和が桁落ちでほぼ相殺）になる
場合、絶対誤差はほぼ一定（入力丸め幅に比例する数 1e-3〜1e-2 オーダー）でも相対誤差は分母がゼロに
近づくことで際限なく増幅されうるため、TF32 入力丸め＋桁落ちキャンセレーションの組み合わせで
十分説明可能である。

### 3.2 絶対誤差救済閾値の再検討（fail セル限定の統計を根拠に）

この場合 `ABSOLUTE_RESCUE_THRESHOLD`（1e-5）による救済が効くべきだが、§2.1 の
`max_fail_abs_diff`（1.2e-3〜2.5e-2）は 1e-5 を 2〜3 桁上回っており救済も効いていない。
旧版は根拠に `max_abs_diff`（全セル対象）を使っていたが、これは「相対誤差で fail していないセル」の
値でありうるため、絶対誤差救済閾値の改定根拠としては不適切である（#186・PR #257 Codex Review
指摘「複合判定の max 値がそれぞれ別要素由来の可能性があり、絶対誤差救済閾値 1e-2 案の根拠として
max_abs_diff は不十分」対応）。§2.1 で TF32 経路の `max_fail_abs_diff` と `max_abs_diff` はほぼ
全形状で一致しており（fail 率が高いため両者が同じセルに由来しやすい）、この点では旧版の結論
（**TF32 特有の丸め特性を前提に、絶対誤差救済閾値をより大きく設定する（`max_fail_abs_diff` の
infimum 実測値 2.535e-2 を厳密に超える値、例えば 1e-2 台後半〜3e-2 台）等の複合指標の改定が必要と
考えられる**）は覆らない。ただし具体的な改定値の決定と REQ-2 改定は本イシューのスコープ外
（§5・§6 参照）。**さらに、この実測値は §1 の計測条件（`Xorshift64Star::fill_vec`／`fill_vec_f16`
が生成する `[-1, 1)` 範囲の入力）でのみ成立する（下記 §3.3 参照）。**

- **f16 WMMA 経路**: K≤256 の範囲では現行閾値内に収まるが、K=512 以降で fail が発生し始め K=4096 で
  fail 率 0.174% まで増加する（§2.2 の K スイープで単調増加を確認）。fail 率自体は小さいが、既存
  `#[ignore]` テスト（`wmma_f16_k4096_stress`）がこの領域で実際に FAIL しているため、**「K が大きい
  場合に現行閾値では不十分」という結論は TF32 ほど深刻ではないものの成立する**。f16 経路は
  `max_fail_abs_diff`（K=4096 で最大 4.883e-4）が `max_abs_diff`（6.250e-2）よりずっと小さく、
  「fail セルを全て救済する」ための絶対誤差救済閾値は TF32 よりはるかに小さい値（infimum 実測値
  4.883e-4 を厳密に超える値、例えば 1e-3 台）で足りる可能性が高い。K 依存の桁落ち蓄積を許容するなら
  絶対誤差救済閾値の緩やかな引き上げ、または K に応じた許容誤差スケーリングの導入が候補となるが、
  これも本イシューでは変更しない。この候補値も §3.3 の入力スケール依存性の制約を受ける
  （`[-1, 1)` スケール限定の暫定値であり、REQ-2 改定の最終根拠には用いない）。

### 3.3 絶対誤差救済閾値候補のスケール依存性（未検証。#186・PR #257 Codex Review 再指摘対応）

§3.2 の絶対誤差救済閾値候補（TF32: 2.535e-2 超、f16: 4.883e-4 超）は、いずれも
`Xorshift64Star::fill_vec`／`fill_vec_f16` が生成する **`[-1, 1)` 範囲の入力のみ**から得た実測値である。

GEMM の絶対誤差は入力のスケール `s`（両行列を `s` 倍した場合）に対しておおむね `s²` でスケールする
一方、相対誤差はスケール不変に近い（TF32 丸めの相対誤差自体はスケール非依存であり、`RELATIVE_TOLERANCE`
側は入力スケールに関わらず妥当性を保ちやすい）。したがって、本ドキュメントが実測した絶対誤差の最大値
（`2.535e-2`・`4.883e-4` 等）を、`[-1, 1)` と異なるスケールのテンソル（例えば実運用の重み・活性化値の
典型的な分布）に対する**固定の絶対閾値としてそのまま適用することはできない**。入力が `[-1, 1)` より
大きいスケールで使われる場合、絶対誤差は `s²` 倍に増幅されうるため、本ドキュメントの絶対閾値候補は
過小評価（救済不足）になる可能性がある。逆に小さいスケールでは過大評価（不要に緩い）になりうる。

**本イシューでは実施していない未実施の検証**（改定値決定前に必要な作業。#186 のスコープ外として
記録し、REQ-2 改定提案時にあわせて実施を提案する）:

- 代表的な複数のスケール `s`（例: 0.1・1・10・100 倍）で同じ形状セット・シード方針の入力を生成し、
  `max_fail_abs_diff` が実際に `s²` に比例して変化するか実測でスイープする。
- または、絶対誤差救済判定そのものを入力スケールで正規化した比較（例: 出力側のスケールに対する
  相対値化）に置き換える設計を検討し、固定の絶対閾値への依存を避ける。

この検証が完了するまで、§3.2・§4 の絶対誤差救済閾値候補は「`[-1, 1)` スケール限定の暫定値」として
扱い、REQ-2 改定の最終根拠には用いない。

## 4. 結論（変更要否）

**変更が必要と判明した**（TF32 経路が全形状で著しく閾値を超過、f16 経路も大 K で閾値を超過）。

- 閾値定数（`RELATIVE_TOLERANCE`・`ABSOLUTE_RESCUE_THRESHOLD`）・既存 parity テストの許容誤差は
  **本イシューでは一切変更していない**（`.claude/rules/coding-rust.md`・`security.md` A08 に従い、
  ユーザー承認なしの緩和は行わない）。
- 改定が必要な場合の候補（ユーザー承認待ち。具体案の決定はスコープ外。**以下の実測値はいずれも
  §3.2 が定義する infimum（この値そのものでは救済されない。丸め前の値を厳密に超える必要がある）
  であり、かつ §3.3 が示すとおり `[-1, 1)` 入力スケール限定の暫定値である。スケールスイープ実測なしに
  REQ-2 改定の最終閾値として採用しない**）:
  1. TF32 経路専用の複合判定（絶対誤差救済閾値を実測ベースで引き上げる。§3.2・§3.3 参照。TF32 は
     `max_fail_abs_diff` infimum 実測値 2.535e-2 を厳密に超える値、f16 は同 4.883e-4 を厳密に超える値が
     候補で、両者の桁が大きく異なるため経路別の閾値が現実的）を REQ-2 に追加する。
  2. f16 WMMA 経路について、K 依存のスケーリングまたは K の実用上限（本ライブラリで許容する最大 K）を
     REQ-2 側で定義し、その範囲内でのみ現行閾値を適用する。
  3. あるいは、TF32/f16 Tensor Core 経路そのものをディスパッチ規則（#66）で高精度要求時に選択しない
     方針とし、経路ごとの精度トレードオフを利用者に明示する。
- 上記いずれも **REQ-2 改定が必要**であり、正本 spec リポジトリ（Fandhe-AI/rust-ai-library-spec）側での
  対応をユーザーに提案する（`docs/spec/` は本リポでは編集しない。`.claude/rules/out-of-scope-tracking.md`）。

## 5. 制約事項

- 本実測は **compute capability 8.6（Ampere、RTX 3060）** によるものである。GB10（sm_121・Blackwell 系譜）
  実機での再確認は #64（TASK-11.1e・open）のスコープであり、Tensor Core の世代差（mantissa 丸め方式・
  累算精度）による差異が出る可能性がある。本ドキュメントの数値をそのまま sm_121 に適用しないこと。
- `mma.sync`/`cp.async` パイプライン導入（#187）後は Tensor Core 経路の実装が変わるため、本実測は
  再評価の対象になる（#187 のスコープ）。
- `tests/cpu_cuda_parity.rs` 冒頭コメントが述べる「naive f16 は複合判定対象外」という既定方針の
  一般化要否について: 本実測は WMMA f16（`CudaWmmaGemm::run_f16`）のみを対象としており、naive f16
  （`CudaGemm::run_naive_f16`）は計測していない。両者はカーネル実装（丸め・累算経路）が異なるため、
  本実測結果を naive f16 に外挿しない。naive f16 の複合判定適用要否は別途実測が必要であり、対象外と
  する（本イシューは WMMA/mma 経路の再評価のみが REQ-2 受け入れ基準の対象）。

## 6. 既存 `#[ignore]` テストの実機実行結果（参考記録）

test wmma_tf32_matches_reference_across_shapes ... FAILED（shape m=32 n=32 k=32:
  複合判定 FAIL fail_count=154/1024, max_abs_diff=1.540e-3, max_rel_err=3.239e-2）
test wmma_tf32_k4096_stress_poc_v2_5 ... FAILED（256x256x4096:
  複合判定 FAIL fail_count=10647/65536, max_abs_diff=2.312e-2, max_rel_err=1.910e0）

$ cargo test -p backend-cuda --test cpu_cuda_wmma_parity -- --ignored --test-threads=1
test wmma_f16_matches_reference_across_shapes ... ok
test wmma_f16_cross_check_against_naive_f16 ... ok

これらの `#[ignore]` テストの許容誤差・判定式は本イシューでも変更していない
（実機依存のため通常 CI では実行されず、`make test-ignored-cuda` 経由でのみ再現する）。
