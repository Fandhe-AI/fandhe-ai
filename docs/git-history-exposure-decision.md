# git 履歴に残存する内部情報・個人メールアドレスの扱い判断（#477）

イシュー #477「git 履歴に残存する内部情報・個人メールアドレスの扱い判断（#461 由来）」に対応する。

**本ドキュメントは暫定方針の記録であり、3 案の最終採否はユーザーの承認による。** 本ドキュメント単体で案 2・案 3 の実行を許可するものではない。

## 背景

イシュー #461（公開前監査）は、追跡ファイル 6 件から内部ホスト名・内部 venv パス等の内部情報をプレースホルダへ置換し、実値を Git 管理外の `.local.md` へ退避する対応（`chore/461-pre-public-audit` ブランチ・コミット c27799e）を含む。**このブランチは本ドキュメント作成時点で `main` へ未マージ**であり、`docs/real-hardware-verification-env.md`（`origin/main` 上の現在の内容）には内部ホスト名がプレースホルダ化されずに残っている。この点は #461 側（追跡ファイルの現在の内容）のスコープであり、本イシュー #477 のスコープ（git 履歴上の過去コミットの diff）とは別事象だが、「マスク対応は完了済み」という誤った前提を残さないためここに明記する。

本イシューが扱うのは、**過去コミットの diff に残る**同種の内部情報と、git 履歴 author の個人メールアドレスである。

## 事実関係（再検証済み）

リポジトリは public 化済み（`gh repo view --json isPrivate,visibility` 実測: `{"isPrivate":false,"visibility":"PUBLIC"}`）であり、`origin` へ push 済みの全 branch（`refs/remotes/origin/*`）は誰でも fetch 可能な公開範囲を成す。したがって以下は `origin/main` に限定せず、**`origin` へ push 済みの全 branch**（実測時点で 23 branch・`git rev-list --remotes=origin --count` = 265 コミット）を対象に再測定した。

他 author（bot アカウント・GitHub noreply 形式・CI 用ダミーアドレス）は個人特定情報を含まないため対象外とした。

## 暫定方針: 案 1（現状維持）

自動運転モードでの安全側の判断として、**案 1（現状維持）を暫定方針とする**。理由:

1. **可逆性**: 何も変更しなければ、後から案 2・3 へ移行する選択肢を残せる。逆（案 2・3 実行後に案 1 へ戻す）は、書き換え前の commit オブジェクトを保持する clone・バックアップが手元にあれば技術的には可能だが、GitHub 側に公開済みの旧コピー（dangling commit・fork 済みコピー・クローラ取得分）はいずれの場合も個別削除依頼なしには回収できない（上表「3 案の比較」参照）。したがって案 1 を維持するほうが、この回収不能性のリスクに晒す範囲を増やさずに済む
2. **実害の限定性**: 残存情報は認証情報を含まない LAN 内ホスト名・パス・個人メールアドレスであり、監査（#461・c27799e 時点）で実秘密は 0 件と確認済み
3. **書き換えの実効性の限界**: リポジトリは既に public 化済みであり、履歴書き換え（案 2）を実行しても GitHub 側キャッシュ（SHA 直指定で到達可能な dangling commit・既存 fork・検索エンジン／クローラの取得済みコピー）には GitHub Support への個別削除依頼なしでは効果が及ばない。「書き換えれば消える」という誤った安心感を残さないよう、この限界を明記する

**最終判断（案 1〜3 のいずれを採るか）は、本 PR のレビューおよびイシュー #477 上でユーザーが行う。** 本 PR はこの決定記録の追加のみをスコープとし、案 2・3 の実行（`git filter-repo`・force-push・visibility 変更・新規リポジトリ作成・author 情報書き換え）は一切行わない。

## 案 2 を選ぶ場合の参考手順（実行は本 PR のスコープ外）

将来ユーザーが案 2 を採択した場合の前提条件・手順の要点（実行は別イシュー・別 PR で改めてユーザー承認を得て行う）。

1. **全共同作業者への事前周知**: 書き換え対象コミットとその子孫の SHA が変化するため、既存 clone をそのまま `git pull` すると履歴が分岐する旨を周知する
2. **`git filter-repo` の実行**: 対象文字列（内部ホスト名・パス）のパターン置換、author メールのプライバシー保護アドレス（GitHub noreply 形式等）への書き換えを、`origin` へ push 済みの**全 branch**に対して一括実行する（`main` のみでは他 branch 経由の露出が残る）
3. **force-push**: 書き換え後の履歴で対象の全 branch を force-push する（branch protection の一時解除が必要になる場合がある）
4. **GitHub Support への削除依頼**: dangling commit・fork 済みコピー等、通常の force-push では到達できない GitHub 側キャッシュの削除を個別に依頼する（依頼しても確実に消える保証はない）
5. **全共同作業者への再 clone の推奨**: 書き換え後の履歴と旧履歴が手元に混在すると事故（旧 SHA への誤参照・意図しない旧履歴の再 push 等）につながりやすいため、再 clone を事故防止の推奨手順とする。技術的には `git fetch` 後に ref を新履歴へ張り替えて継続利用する方法もあるが、確実性を優先するなら再 clone が簡便である
6. **外部参照の棚卸し**: Issue・PR 内の SHA 直リンク、ドキュメント・CI badge 等の外部参照が新履歴でも有効か確認する

## 再発防止策

- **noreply メールでのコミット推奨**: 個人メールアドレスでの author 記録を避け、GitHub 提供の noreply メールアドレス（`<id>+<username>@users.noreply.github.com` 形式）を既定の commit author とする運用を推奨する
- **追跡ファイルの内部情報マスク運用の継続**: `.local.md` 方式（内部情報は Git 管理外の `.local.md` へ退避し、追跡ファイルにはプレースホルダのみを残す。`.gitignore` 対象・テンプレートは `.local.md.example`。#461・`chore/461-pre-public-audit` ブランチで導入・本ドキュメント作成時点で未マージ）のマージ後、今後新たに内部ホスト名・パス等を記載する必要が生じた場合はこの方式に従う

## マスク方針（本ドキュメントの記述ルール）

#461 が追跡ファイルから内部情報を除去する方針と整合を保つため、本ドキュメントには内部ホスト名・venv パス・個人メールアドレスの**生の値を記載しない**。該当箇所はイシュー番号・コミット SHA（例: 「イシュー #461・#477 記載の内部ホスト名」「git 履歴 author の個人メールアドレス 1 件」）への参照で間接的に指す。詳細値は private な Issue コメント・`.local.md` 側にのみ存在させる。

## 検討済み・不採用: `.mailmap` の追加

`.mailmap` によるコミット author 表示名の正規化を検討したが、**不採用とした**。`.mailmap` は追跡ファイルであり、個人メールアドレスを対応表として新規に追跡ファイルへ記載することになるため、履歴上の露出を除去するどころかむしろ増やす（現在は履歴の diff 内にのみ存在する情報を、`HEAD` の追跡ファイルとして常設することになる）。この理由により、案 1・案 2 のいずれとも独立に不採用と判断する。
