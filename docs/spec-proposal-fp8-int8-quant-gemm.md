# FP8/INT8 量子化 GEMM の REQ 追加提案（草案）

> **本文書は spec リポジトリ（Fandhe-AI/rust-ai-library-spec）への REQ 追加**提案の草案**であり、正本ではない。
> 採否・spec 側への起票判断は人間（ユーザー）の承認事項（イシュー #584）。本リポジトリの
> `docs/spec/`（正本 submodule）は本提案作成にあたって一切編集していない。**

出典: GEMM 性能改善ツリー #479・Phase G（#582）子タスク G-1（`human-required`・P0・実機不要）。

## 1. 目的・位置づけ

- 対象は Transformer 複合ワークロード（`docs/performance-targets.md`）の改善軸としての量子化 GEMM であり、
  GEMM 単体 5 形状の下限（REQ-8）には寄与しない設計判断とする（#582 冒頭整理を踏襲）。
- REQ-8 は複合ワークロード行に下限を設定しない方針のため、本提案は REQ-8 の既存下限値を変更しない。
- 現行 REQ の対象精度は f32／f16 のみであり、FP8／INT8 は REQ 範囲外。本提案は新規 REQ の追加を提案するもので、
  既存 REQ-2（バックエンド間数値一致）・REQ-8（性能下限）の改定は扱わない（8 節「相互参照」参照）。

## 2. 対象精度

- **FP8**: E4M3（順伝播系の候補）・E5M2（勾配系の候補）。
  **累積は fp32 常時累積を必須条件とする**。これは DeepGEMM の SM90 FP8 GEMM 実装が採る方式を参考根拠として
  自分の言葉で要約したものであり、コードは流用しない（#479 共通方針・ライセンス境界）。
- **INT8**: `s8 × s8 → s32`。4 節の候補命令（`mma.sync.aligned....s32.s8.s8.s32`）が示すとおり積和は s32 に
  累積される。よって INT8 経路は fp32 常時累積を要件としない。**s32 累積の結果に対してスケール（amax 由来の
  量子化スケール）を適用したうえで fp32 へ変換する**契約とする。fp32 常時累積は FP8 経路のみの要件である。

## 3. 数値許容基準の提案

量子化経路は f32 参照に対し既存 REQ-2 複合判定（相対誤差 1e-3 未満 または 絶対誤差 1e-5 未満。
`.claude/rules/coding-rust.md`）を満たし得ない。よって：

- **既存 tolerance の緩和ではなく、量子化経路専用の別基準を新 REQ として定義する**方針を提案する。
  例: quantize-dequantize 参照実装との一致判定 ＋ f32 参照とのスケール前提付き誤差上限。具体閾値は
  spec 側で実測のうえ確定する段取りを提案する。
- REQ-2／REQ-7 の既存閾値には一切触れない。tolerance 変更は spec 改定とセットの人間承認必須事項
  （REQ-5・`.claude/rules/coding-rust.md`）であることを明記する。
- **スケール計算の前提条件**: amax を 1e-4 程度へ下限クランプすることで、スケール計算（`1 / amax`）における
  ゼロ除算・極小 amax に起因する極端な（オーバーフロー方向の）スケール値の発生を回避する（TileKernels の
  スケール集約実装が採る前提を参考として要約。コード流用なし）。このクランプは amax（絶対値の最大値であり
  非負）の下限を持ち上げる処理であり、**非正規化数・符号付きゼロ・NaN／Inf の入力値そのものを排除する処理
  ではない**点に注意する。入力に非正規化数・符号付きゼロが含まれる場合の扱いや NaN／Inf の検出・拒否は、
  amax クランプとは別の入力検証として spec 側で個別に定義する。
- **fine-grained scaling**: per-token スケール、および K=128 ブロック単位のブロックスケールを設計前提とする。
  スケール自体は power-of-2 丸め（ビット演算のみで実現可能。除算・浮動小数点丸めモードに依存しない）とする。

## 4. sm_121（GB10）で使える MMA 形状

CUTLASS の SM120 mainloop は narrow-precision 専用の `mma.sync.aligned.kind::f8f6f4` 系に限定される
（SM120 ビルダーの static_assert が根拠）。これを踏まえ、候補形状を以下のとおり整理する。

| 精度 | 候補命令 | 備考 |
|------|---------|------|
| FP8 | `mma.sync.aligned.kind::f8f6f4`（m16n8k32 系） | SM120 mainloop 限定形式 |
| INT8 | `mma.sync.aligned.m16n8k32.row.col.s32.s8.s8.s32` | sm_80 以降で利用可能 |

**未検証事項（明示）**:

1. NVRTC の `compute_121` 受理可否は未検証（`docs/cuda-tensor-core-knowledge.md` 2 節・8 節に既存の
   未検証事項として記録されている事実と同根）。
2. SM100 以降前提の 32 バイト幅ベクトルロードが sm_121 で発行可能かは未確認（#582 の G-16 注意書き）。

上記 2 点は、実機検証イシュー（#408 系列）の A-2 実機プローブへの相乗りを提案する。

## 5. 期待効果

f16 比でデータ幅半減（帯域）、および Blackwell 世代 Tensor Core の FP8 スループット向上という一般論のみを
記載する。実測値は未取得であり、数値の断定はしない。実測確定は G-17（量子化 GEMM 試作。本提案が承認された
場合にのみ起票）に委ねる。

## 6. 非採用時の代替

本提案が spec 側で不採用となった場合は、現行 f32／f16 経路を継続し、Phase G の融合カーネル
（RMSNorm／online softmax 等）のみで複合ワークロードの改善を図る案を代替とする。この場合 G-16
（量子化キャストカーネル）・G-17（量子化 GEMM 試作）はいずれも起票しない。

## 7. 依存追加の要否

`half` crate は f16／bf16 のみを扱い FP8 型を持たない。そのため **FP8 型は `u8` ベースの自作 newtype
（ビット変換を自作実装）で表現し、許容依存 8 区分（`.claude/rules/deps-policy.md`）の範囲で完結する**
案を推奨し、依存追加は不要と結論する。

仮に外部 FP8 crate を採用する案を選ぶ場合、それは deps-policy.md により**別途ユーザー承認が必須の事項**
となる旨を併記する。本提案では自作案を推奨する。

## 8. 相互参照・提案の一本化

- **F-7（#580）**: REQ-2 複合判定改定＋REQ-8 表更新の提案（`docs/spec-proposal-req2-req8-revision.md`
  として草案完成済み）。本提案は REQ-2／REQ-8 の既存値そのものの改定を扱わない点でスコープが異なる。
- **G-5（#591）**: `kernel-fusion.md` 方針（REQ-12 整合）の改定要否判断。本提案は REQ-12 の改定を扱わない。
- 本提案のスコープ境界: **新 REQ の追加提案であり、REQ-2／REQ-8 の既存値・REQ-12 の改定は扱わない**。
- spec 側へは、無調整で複数件を別々に起票せず、**F-7（#580）の提案と調整のうえ 1 回にまとめて起票する**
  運用を提案として記載する。

## 9. 結論

本提案が spec リポジトリ側で REQ として承認された場合にのみ、G-16（量子化キャストカーネル）・
G-17（量子化 GEMM 試作）を追加起票する（#479・#582 で確定済みの条件付き起票ルールの再掲）。
承認前に本リポジトリで量子化カーネルの実装コードに着手することはない。
